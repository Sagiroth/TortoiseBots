# Dungeon Run Leader

> Work in progress. These features are not officially released and not supported yet. Enable them at your own risk. Until the official release, bug reports and feedback about them are not handled through the issue tracker; contact Hypeer directly.

A **dungeon plan** is the route of one dungeon written as data: where to walk, which packs to pull, which bosses to kill, which objects to open and what to wait for. Plans are made and checked live by [turtle-agent](https://github.com/pjerra/turtle-agent) (its `dungeons/<name>.json`, plan format v1); its exporter turns them into world migrations for the tables below. The turtle-agent file is the single source: edit the plan there and export again, never the rows by hand.

The **run leader** (`.bot run`) lets a bound party clear such a plan by itself. It is **off by default** (`AiPlayerbot.DungeonSelfClear = 0`); see [Run leader](#run-leader) below.

The tables are read at startup into a cache (`ai/playerbot/DungeonPlanMgr.cpp`, one pass per table). Nothing reads them per tick. Until 2026-10-22 a change needed a restart; since then a GameMaster reloads them with `.bot run reloadplans` (below).

### Reloading the plans (`.bot run reloadplans`)

Added 2026-10-22 (owner goal: fix a plan blocker by a hot reload instead of an image rebuild and a server restart per fix). A GameMaster in game, or the server console, remote access or SOAP with an account of that rank, sends `.bot run reloadplans`. It works with the run leader off too. The gate was `SEC_GAMEMASTER` (account security at or above it, in game or on the CLI handler); this core has no separate GM rank, and the module's compat shim (`ai/cmangos-compat-shim.h`) defines `SEC_GAMEMASTER` as `SEC_DEVELOPER`, which is **3** in the core's `AccountTypes` (0 player, 1 observer, 2 moderator, 3 developer, 4 administrator, 6 console). Until 2026-10-26 it was `SEC_ADMINISTRATOR` (4), and a rank-3 GM account was refused with `forbidden`. On the world thread, in the command, the module read `ai_dungeon_plan`, `ai_dungeon_leg`, `ai_dungeon_step`, `ai_dungeon_boss` and `ai_boss_tactic` again through the same loaders and row checks as at startup, into NEW tables, and then:

- **Refused** when a query failed or a table changed while it was read, or when any row was refused (a plan, leg (an unknown plan, a second row of a leg number), step, boss or boss tactic row skipped, a plan whose `cc_priority`, `cc_always` or `kill_first` did not parse), or when a plan of the loaded set was gone or had no steps any more: the old set stayed, nothing changed, and the answer was `TBM:ACTION_ERR|run reloadplans|refused|Dungeon plans NOT reloaded, the old set stays: <reason> (the database now reads: Loaded ...)`, naming the first three refused rows (the server log named every one). The core's world database answers an empty result and a failed query alike and spreads queries over a pool of connections with no read transaction, so the five reads could not share one snapshot: the reload read each table's row count and a sum of a CRC32 of the loaded columns (`SELECT COUNT(*), ...`, which always answers one row) before the first data query and after the last one, and refused with *the read of <table> failed* when such a query failed or fewer rows came back than the count, and with *<table> changed during the reload* when the two revisions differed (a migration still being applied: send the reload again once it is in). At startup such rows were skipped with an error line (a leg row too, since 2026-10-22 with an error line of its own) and the boot stayed as lenient as before; a reload was stricter, since the old set worked. A plan could therefore not be removed by a reload: that still took a restart.
- **Accepted** otherwise: both new tables replaced the old ones at once, and the answer was the boot log's line with `reloaded` (`Loaded 11 dungeon plans, 3340 steps, 70 dungeon bosses (0 plans, 0 steps and 0 boss rows skipped), reloaded (dungeon bosses 70 -> 71, boss tactic rows 59 -> 59)`), one `Plan changed:` line per new or changed plan (`bfd 620 -> 622 steps`, `uldaman 139 steps, rows changed`, `rfk new, 80 steps`; `Plans changed: none` when nothing differed), and `Boss spawn cache rebuilt in N ms for M maps`: the dashboard's boss list was built again from the new boss rows, by the same one pass over the spawn data as at startup. It ended with `TBM:ACTION_ACK|run reloadplans|plans|<count>|-`.
- **A run in progress kept the plan it started with.** A run holds a pointer into the plan table it started from, so the replaced table was kept alive (not freed) while any run's plan pointed into it, checked again on each reload; the answer then said how many runs kept their plan. `.bot run stop` and a new `.bot run start` took the new plan. Nothing held a boss tactic row across a tick, so the new tactic rows applied at once, also to a run in progress.

Rules: `ai/playerbot/DungeonPlanReloadPolicy.h` (tests `tools/test_dungeon_plan_reload_policy.cpp`); wiring pins `tools/test_reload_plans_wiring.py`.

## Tables

The schema comes from `data/sql/world/20261014150000_world.sql` (schema only; the rows come in the exporter's own migrations).

### `ai_dungeon_plan`

| Column | Meaning |
| :--- | :--- |
| `plan` | The plan's name, lower case (`uldaman`). Primary key. |
| `map` | The instance map id (Uldaman 70). |
| `source` | Where the rows came from (the turtle-agent commit and file), for the reader. |
| `comment` | Free text. |

### `ai_dungeon_leg`

| Column | Meaning |
| :--- | :--- |
| `plan`, `leg` | The plan and the leg number (0, 1, ...). Primary key. |
| `name` | The leg's name in the plan (`baelog`, `keystone`), shown in the status line. |
| `comment` | Free text. |

### `ai_dungeon_step`

One row is one thing to do. Steps run in `(leg, seq)` order; the primary key is `(plan, leg, seq)`.

| Column | Meaning |
| :--- | :--- |
| `plan`, `leg`, `seq` | Where the step sits. `seq` need not be dense. |
| `kind` | What to do (table below). |
| `entry` | A creature, game object or item entry, by kind; `hold`: the instance data index or the game object of its done condition; `gossip`: the NPC's creature entry. |
| `x`, `y`, `z` | A point on the plan's map, by kind. |
| `radius` | Yards, by kind; at most 100. |
| `item` | An item entry, by kind; `0` for none. |
| `param` | `wait_object`: the state to wait for (`0` ready / closed, `1` active / open, `2` active_alt). `ritual`: how many bots use the object (`0` = 3). `open`, `use_item`: a second item the step needs in the same bags (`0`: none; Uldaman's Medallion use needs the Shaft of Tsol 7741). `hold`: the value of its done condition. `gossip`: the option to pick, counted from 1 at the top of the NPC's menu as `.bot cmd gossip` takes it (1-15). |
| `flags` | `1` ambush (a stealthed pack), `2` Alliance only, `4` Horde only. `hold`: `8` done by instance data, `16` done by object state, `32` the data is an encounter state (see [Events](#events)). `move`: `64` an **exact** waypoint (see [Exact waypoints](#exact-waypoints)); on any other kind the row is refused. `loot`/`open`/`wait_object`: `256` the object being **gone** counts as done (see below); on any other kind the row is refused. `gossip`: `512` the NPC being **dead** counts as done (see the `gossip` kind below); on any other kind the row is refused (`128` is reserved). `pull`: `1024` **no_defer**: a pack not reachable from the party's floor pauses the run instead of being deferred (see the 2026-10-23 Windhorn Canyon entry below); on any other kind the row is refused. `open_proof`: `2048` the proof is a living creature (else a spawned game object); on any other kind the row is refused. |
| `timeout_s` | `wait_object`, `wait_clear`: seconds before the wait fails; `hold`: the event's ceiling, fights included; `gossip`: how long the answer is waited for. `0` = 60, at most 600. |
| `entries` | Comma-separated creature entries (`4851,4852`), by kind; at most 16. |
| `comment` | Free text. |

### Step kinds

| Kind | Columns used | What it means |
| :--- | :--- | :--- |
| `move` | `x y z`, `flags` (`64` exact), `entry` (an area trigger) | Walk on the navmesh to the point. A plan leg's `to` and every via point of the route are moves. With flag `64` the lead bot must stand on the point (1.5 yd, 2 s still) before the next step goes out: [Exact waypoints](#exact-waypoints). Since fix/plan-gossip-allow `entry` named the area trigger the step walks into (0 = none): from the step on (also once the run had gone on to the boss or a detour's stand-in) until it had fired once for the run, its bots fired that trigger's script although `AiPlayerbot.BotAreaTriggers` did not list it (Zul'Farrak leg 10 seq 101, `962` at_zumrah, migration 20261024000000), and no other unlisted trigger. A trigger whose script refused (it returned false: at_zumrah while Zum'rah stood farther than 30 yd) stayed armed and each bot inside tried it again every 2 s; it counted as fired only once its script ran. A run started past the trigger's move step (`.bot run` from a later step) never armed it: when the event had not happened, the run was started again from before that step. |
| `move_direct` | `x y z`, `entry` (an area trigger) | Walk a straight line to the point (a short gap the navmesh does not bridge). `entry` as for `move`. |
| `move_hop_exact` | `x y z` | A `move_direct` launched from the exact `move` (flag `64`) right before it in its leg: it goes out only on that point's proof. Its own kind so that a module without exact waypoints skips the row and sends no direct order for it (the migration and the module are deployed together): [Exact waypoints](#exact-waypoints). |
| `pull` | `x y z` (centre), `radius` (0: 15), `entries`, `flags` | The pack: every living unit of `entries` within `radius` of the centre. `flags 1`: the pack is stealthed; the party walks through it and fights what shows. |
| `boss` | `entry`, `x y z`, `entries`, `radius` (0: 30), `flags` | Kill `entries` in that order, then the boss `entry`. |
| `loot` | `entry`, `x y z` (near), `item` | Loot a chest or a corpse of that entry near the point; `item` must be in the bags afterwards. |
| `open` | `entry`, `x y z` (near), `item`, `param` | Use a game object (a door, the Keystone); `item` is what its lock needs; `param`, when set, a second item it needs. |
| `open_proof` | `entry` (the object used), `x y z` (its point; the proof is searched around it), `entries` (exactly one: the proof entry), `radius` (the proof radius, over 0 and at most 20), `flags` (`2048` the proof is a living creature, else a spawned game object) | Use the object as by `open`, and the step is done once the proof stands within `radius` of the point after the use's task answered: at most 5 s (`kOpenProofWaitMs`), then the run pauses. Sunken Temple's Atal'ai statues (148830-148835) change no state when used; the right one respawns the green light 148883 beside it, which is the proof. `param` and `timeout_s` must be 0; a game-object proof that equals `entry` is refused, and flag `2048` on any other kind is refused. A module without it refuses the row (`UnknownKind`). |
| `use_item` | `entry` (the item), `item`, `param` | Use an item from the bags; `item` is what the use must make; `param`, when set, a second item the use needs. |
| `wait_object` | `entry`, `x y z` (near), `param`, `timeout_s` | Wait until the object is in that state (the Seal of Khaz'Mul opens). |
| `wait_clear` | `x y z`, `radius`, `timeout_s` | Wait until no living hostile stands within `radius` of the point (2D): every hostile in the radius holds the step, whatever its height, so a required mob idling on another level still waits until it targets the party. Only past `timeout_s`, when every hostile left is a bystander on another floor (none engaged with the party — its victim or an attacker is a party member — and all more than 10 yd above or below the spot), the step finishes with the note `the spot is clear on its floor` instead of pausing; anything engaged or on the spot's floor pauses as before. |
| `rest` | — | A rest gate even when nobody is low. |
| `ritual` | `entry`, `x y z` (near), `param` (bots, 0: 3) | A summoning ritual object several bots use together (Uldaman's altars): an event's start. |
| `hold` | `x y z` (the spot), `radius` (0: 30), `entries` (the event's units), `entry` + `param` + `flags` (the done condition), `timeout_s` | A scripted event: stand on the spot and fight what comes until it is done. See [Events](#events). |
| `gossip` | `entry` (the NPC), `x y z` (near), `param` (the option, 1-15), `timeout_s` | The lead bot talks to the NPC and picks one option of its menu: the order `.bot cmd gossip <entry> <lead bot> <param>` ([commander](commands/commander.md#bot-cmd-gossip)). The NPC is searched within 40 yd of the bot; the lead bot first walks to the point when it is farther than 30 yd from it (navmesh hops while it is out of sight). The ACK ends the step; an error pauses the run with the module's own words (an NPC that `AiPlayerbot.BotGossipNpcs` does not list is `not-allowed`, and the words name that key; since fix/plan-gossip-allow that no longer held for the step's own NPC: a bot of a running or paused run was let talk to the entry the run's current gossip step names (its `entry` only: the step orders no other), read from the loaded plan, without the list, after Shadowfang Keep r27 slot7 stopped at step 130/313 on *cmd gossip 3849 ... refused: not-allowed* at its own Deathstalker Adamant step; another NPC, or the same NPC while the run stood at any other step, was still refused; a dead NPC of the entry within 40 yd and none alive there is `no-npc` with the dead one's name and respawn time in the words, and the run pauses at once with *gossip N option M cannot be done: none alive within 40 yd, a dead one lies nearby (<name> (<entry>), respawns in ...). .bot run resume will not help while it lies dead; .bot run skip ... .bot run stop ...*, the same for the late failure of an NPC that died on the way; the words claim nothing about one farther than 40 yd, and a scripted NPC with no respawn timer says so instead of a time); no answer in `timeout_s` pauses it too. It ends on the order's ACK, not on what the option did: put a `wait_object` (the door) or a `hold` after it. A gossip right before a `hold` starts that event, as `open` and `use_item` do. The one flag read is `512` (`kPlanFlagDeadNpcIsDone`, **dead is done**): with it, the dead-NPC refusal (or late failure) above did not pause the run but ended the step as done, note *gossip 7604: Sergeant Bly lies dead, nothing to talk to: the step is counted done (the plan marks a dead NPC as done)*; without it the step pauses as described. Only that wording counts: every other refusal or failure (`not-allowed`, a plain `no-npc`, a missing option) paused the run as before. Zul'Farrak's Sergeant Bly (7604) carries it, since the pyramid event's troll waves killed his crew before the Bly leg in 2 of 3 runs (r12, r15) and the run then needed a manual skip; Weegli (7607) does not, since the End Door cannot be opened without him. Any other flag on a gossip row is refused. |
| `use_on` | `entry` (the game object), `x y z` (near; required), `item` (the item used on it), `timeout_s` | The carrier (the party bot that carries `item`, the lead bot first) uses `item` ON the object: the order `.bot cmd use <item> <carrier> entry:<entry>@x,y,z`, which walks the bot to the object and casts the item's spell at it (a key item whose spell opens the object's lock: Zul'Farrak's gong 141832 with the Mallet of Zul'Farrak 9240; a plain `open` of the gong does nothing). Added 2026-10-21. No flag or param is read: a set one is refused. |

The loader skips a row it cannot use and names it in the server log (`ai_dungeon_step: plan ... skipped`): an unknown kind, a `pull` without entries, a `boss`/`loot`/`open`/`use_item`/`wait_object`/`ritual`/`gossip`/`use_on` without `entry`, a `gossip` with `param` outside 1-15 or with a flag other than `512`, a `use_on` without `item`, without a point (0 0 0) or with a flag or `param` (a module from before `use_on` skips the row as `UnknownKind`: the run then goes on without the use, loudly logged), a negative or over-100 radius, a `wait_clear` without one, a timeout over 600 s, a `wait_object` state above 2, the exact flag (64) on a step that is not a `move` (an unknown kind, `move_hop_exact` on a module before exact waypoints, is skipped as `UnknownKind`), the gone-is-done flag (256) on a step that is not a `loot` or an `open`, the dead-npc-is-done flag (512) on a step that is not a `gossip`, a `hold` with both done flags (8 and 16), with flag 32 but not 8 or an encounter state above 4, done by object without `entry` or with a state above 2, or with neither done flag and no `entries`, a duplicate key, or a step of a plan with no `ai_dungeon_plan` row, or an `entries` text that is not a comma list of non-zero entries (`BadEntries`). It also logs a plan whose consecutive moves are more than 60 yd apart (the exporter should cut such a leg into via points). The rules are `NormalizePlanStep` in `ai/playerbot/DungeonPlanPolicy.h`; `tools/test_dungeon_plan_policy.cpp` and `tools/test_dungeon_plan_sql.py` test them.

On 2026-10-21 the commander telemetry got a boss list: the `boss` steps' `entry` and the rows of the world table `ai_dungeon_boss` (`map`, `entry`, `name`; read with the plans), and a unit on that list was reported with `rank` `b`, because a five-man boss carries creature rank 1 and no instance bind, so the dashboard map had crowned none (the adds of a step's `entries` stayed `e`). The table lists the bosses of the dungeons that have a plan (Ragefire Chasm, Wailing Caverns, Uldaman, Zul'Farrak, Deadmines), with the ones no boss step names such as Kresh, Mutanus, Archaedas, Gahz'rilla, Sneed and Cookie and Turtle's Wailing Caverns uniques Vangros and Zandara Windhoof; other dungeons are added as their plans arrive.

## Joining a bot LFG group

While a bot LFG group waits for its fifth member, its leader posts one line in your faction's LookingForGroup channel, again every few minutes: `LF1M tank Deadmines 17-24, w me inv`, `Deadmines need tank (17-24), /w inv`, or `LF tank for Deadmines, lvl 17-24, whisper inv`. Whisper the leader `inv` to join.

You get the invite when you are the group's faction, inside its level band, and your class and talents fit the open role (only damage fits everything; a tank or healer needs a class that can play it and talents leaning that way, unless you spent fewer than 10 talent points). Otherwise the leader answers once: the group is full, someone else is joining, leave your group first, the wrong level band, the wrong role, hardcore characters are refused, or your earlier invite fell through and the slot is already taken. Only one player is invited at a time, and the invite waits 60 seconds for you to accept; once the slot is taken the posts stop.

## Run leader

Owner decision (2026-10-14, in force since 2026-10-25): the run leader is on by default. It needs `AiPlayerbot.DungeonSelfClear = 1` (default `1`) and a binding (`.bot commander bind <LeadBot>` for a bot-led party, `inparty` for your own party, or the server's own system binding): the run leads the bound party, nobody else's. The commands and the `TBM:RUN` status line are in [Player Controls §1b](commands/commander.md#run-leader-bot-run).

**Starting partway** (`.bot run start [plan] from <leg|step>`, player-controls §1b): the run begins at the first step of a leg (`from 4`, `from leg trogg_west`) or at a step number (`from step 57`) instead of the start, for a party that is already inside the instance (a retry after a failed run, a hand-walked party). The server checks that the lead bot is on an instance map and the whole commanded party in its instance, and says so in its reply; the steps before are neither done nor checked, (a start inside a scripted event goes back to the step that starts it, so the ritual is not skipped), so doors they would open and items they would fetch are the caller's business. Without `from` the run starts at step 1 as before.

**Time limit:** `AiPlayerbot.DungeonRunMaxMinutes` (default 180, `0` = none) ends a run that has lasted that long since `run start` (a pause counts) with the note `time limit reached (3h)`; it is not a stop by hand. A driver with a limit of its own can pass its reason to `.bot run stop <reason>`.

**Items and keys a run needs** (the plan's `ai_dungeon_leg_need` rows, read at startup and by `.bot run reloadplans`): an *optional* leg runs only when someone in the party carries its item, else it is skipped with a note at its first quiet tick (Zul'Farrak's gahzrilla leg needs the Mallet of Zul'Farrak 9240); a *door* leg with a key nobody qualified carries warns once at the start (naming the key, the Lockpicking skill when one opens it, and where to get it) and HOLDS the bots once they come within 25 yd of the closed door (one need row per door, on the leg that crosses it) until it reads open: the run then goes on by itself (`.bot run resume` keeps the hold while the door is closed; `.bot run skip` walks the party past it by hand); a party member carrying the key (a real player) or a real player's Lockpicking that reaches the lock means no hold; a *blocking* item nobody carries warns at the start and asks at the use step. The warn/hold/skip check is always on. `AiPlayerbot.DungeonRunGiveItems` (default `1`): a bot-only run GIVES every needed item to every bot at the start and TAKES it back at done, stop, erase, a bot leaving, or a real player joining (the exact given item instances, soulbound so they cannot be traded, mailed or sold, are recorded in the crash ledger `ai_run_given_item` before the bot holds them and destroyed at the bot's login after a crash; a bot's own copy of the item is never taken). `AiPlayerbot.DungeonRunBotKeysForPlayers` (default `0`): when `1`, bots also carry the needed dungeon keys/items in a party WITH real players and open the doors for them (players skip the key content: the bot carrying the key opens the door near it with the `open` order, three tries 20 s apart, then the hold asks the player); `0` = players must bring their own key, the bots stop at the door and ask.

**Test speed** (owner request 2026-10-25): `.bot run start ... speed=<1.0-3.0>` let a GameMaster's bot-only test run walk faster; a fight, a pull out or being set up, a rest, a meal, an event and a pull or boss step's pack in sight put the party back to 1.0 at once, and the rate came back after two clean ticks. Swimming stayed 1.0. A real player in the party refused it at the start and blocked it for the rest of the run. From 2026-10-27 (pip S3) the refusal named the reason that held for anyone first: a player-led run, then a real player in the party (both `real-player`), and only then a commander who is not a GameMaster (`forbidden`, *...; without speed= the run walks at normal speed*); and `speed=` could stand anywhere among the start's words, after `player tank <Bot>` too (that order had been a Usage error). Passing packs faster could not add pulls but could miss a body pull a 1.0 walk would make (the core checks aggro about once a second), so only 1.0 runs were clears. At test speed the lead bot also waits for the party while walking: once a living bot falls more than 25 yd behind, the walk holds on the spot and walks on when every living bot is within 20 yd or after 30 s (never at 1.0, after a real player joined, on a direct step, with the lead bot in water, in a fight or an event; tests TestSpeedLeashHoldsAFastWalkForAStraggler through TestSpeedLeashClearedByANewStep). From 2026-10-28 (Karazhan Crypt kcleg6-t1028 step 293: the lead bot swam under the shaft's ramp lip but was not read as in water, and `cmd move` lifted its own spot onto the ramp above and refused it unreachable) a refused hold paused no run: the walk under way went on and the leash was spent for that step (TestSpeedLeashRefusedHoldWalksOn).

It is the **observe** mode of the dungeon modes: the bots clear, the commander (a player, or turtle-agent with `--mode observe`) only watches the status line and the `TBM:VIEW` feed, and may pause, skip, resume or stop.

### How it plays

Once a second the run reads the party (alive, dead, in combat, health, mana, spread) and the current step's surroundings, and the step machine (`runtime/DungeonRunPolicy.h`) answers with at most one order. The order is sent exactly as the commander's own `.bot cmd <order>` (`move`, `move ... direct`, `pullback`, `rest`, `loot`, `open`, `use`, `ritual`): same checks, same ACK/ERR lines. The fights are the bots' own combat AI, with the [boss tactics](boss-tactics.md) of a bound party.

After an ACK (or 90 s without an answer) the step is latched for the run: a wipe or the lead bot's death replays it without a second use, because a second ring summons a NEW Gahz'rilla that the instance kills at once (instance_zulfarrak.cpp:185-190 DisappearAndDie), leaving a dead, invisible 7273 at the pit that a boss row can take for his death. |
| `wait_object` | Reads the object's state near the point (like `cmd state`) until it matches; `timeout_s` then pause. The state is compared exactly (`0` ready, `1` active, `2` active_alt): a script that opens its door with the alternative state needs `param` 2 (Zul'Farrak's End Door 146084, which Weegli's blast opens with `DoUseDoorOrButton(..., 0, true)`, zulfarrak.cpp:423: the r8 run paused twice at a param-1 wait on a door that was open, state 2). With flag `256` the step was also done by the object being **gone**: it read not found near the point for 3 s without a break (three ticks) after a wait step had read that target found earlier in the run (a target is the entry with the step's point, within 10 yd), with the note `is gone after it was seen: counted as done`. A not-found counted only when the search could have found the object: the lead bot alive and in the world on the plan's map, the step's point within `AiPlayerbot.ReactDistance` of it and its grid loaded; a dead or released lead bot, another map, a point too far or an unloaded grid never counted, and started the 3 s over. A flagged wait over a stale combat flag was finished by a confirmed gone object as it is by the wanted state. An object never seen still waited out `timeout_s` and paused. Shadowfang Keep's Courtyard Door 18895 carries it, since Deathstalker Adamant's escort sets the door active and removes it a few waypoints later. |
| `wait_clear` | Walks to the spot if needed; waits until no living hostile is within the radius (2D): every hostile in it holds the step, whatever its height, so an event mob on a ramp, one fighting the party from above, or a required mob idling on another level still holds it. Only past `timeout_s`, when every hostile left is a bystander on another floor (none engaged with the party and all more than 10 yd above or below the spot), the step finishes with the note `the spot is clear on its floor` instead of pausing; anything engaged or on the spot's floor pauses as before. |
| `rest` | `cmd rest` and waits as the rest gate does. |
| `ritual` | `cmd ritual entry:<id>@x,y,z <lead bot> <bot> <bot>` with the lead bot and the nearest living bots, `param` in all (fewer up: pause). Its one answer decides: ACK, the step is done (the event started); ERR pauses with the module's words. Bots free again with no answer for 5 s: pause. |
| `hold` | See [Events](#events). |

The lead bot carries a ritual. A loot goes to the lead bot, or to the bot a refusal moved it to. An open or use_item goes to the bot that carries all of the step's inputs (the lead bot first); once its order is out, that bot stays the carrier until the step ends (its answer and the made item are read from it, though the use consumed the inputs), unless it left the party, died or left the map.

### Exact waypoints

A `move` row with flag `64` is the point a direct step after it is launched from (plan v1's `via[k].exact`). Wailing Caverns leg 10 (`serpentis`) is the case: the hop from the foot (-293.3 0.5 -58) down to the Lord Serpentis ramp (-287.5 5.0 -63.6) was proved live only from the foot itself (2026-10-18, wc-hop-probe-2); a direct step sent from a few yards short is refused `no-los` or lands short of the gap, over a 47 yd drop. The foot row is 2.25 yd from the row before it, so the plain rule (done within 3 yd, or within 6 yd after a 3 s stall) would count it done without a step and launch the hop from wherever the lead bot stood. The rule, pure policy in `runtime/DungeonRunPolicy.h` (`ExactWalkTo`, same numbers as turtle-agent's remote driver `tightenTo`):

- **Walk:** the plain walk to the point (its tries and its stuck pause). Its 3 yd or stalled 6 yd arrival only starts the *tighten*; a refused move takes no stand-in point (no detour) and pauses.
- **Tighten:** orders only while the lead bot stands (`Facts::leadMoving`, the lead's `Unit::IsMoving`, and a move of more than 0.5 yd between two looks), after 3 s of standing off the point. Farther than 6.5 yd from it on the ground plane: `cmd move` onto the point again. Nearer (the module carries out no plain move under about 6 yd on the ground plane, turtle-agent `MinMove`): back first to the latest plan `move` point before it that is at least 6.5 yd from the lead bot and from the point on the ground plane and within 60 yd (never back over a direct step), then onto the point. At most 3 moves onto the point (`exactRounds`); the moves back to the point behind are not counted, they are bounded by the 36 s ceiling alone.
- **Proof:** the lead bot within **1.5 yd** of the point, not moving (no 0.5 yd move between two looks either), and within 0.5 yd of one spot for **2 s** of looks (three ticks). At the exact `move` step the step is then done and its route checkpoint set; a proof taken again inside the hop's own check (below) sets no checkpoint, the hop's arrival does.
- **Bound:** no proof within **36 s** out of combat (the walk's 12 s × 3 tries) pauses the run: *the exact point of step N (x y z): the lead bot was not proved to stand on it within 36 s (… yd away, …); the next step is not sent from short of it: put the lead bot on the point (within 1.5 yd), then .bot run resume*. A fight starts the tighten and the proof over.
- **The hop checks it too:** a `move_hop_exact` (or a `move_direct` whose step before is exact) goes out only while that proof stands (the proof of that step, the lead bot still within 1.5 yd); otherwise, after a resume, a start at the hop, a fight or a walk back, the tighten runs again first (a fight and a pause always clear the proof). A walk back replays an exact point the same way. A `move_hop_exact` with no exact move right before it in its leg pauses the run (*… is a move_hop_exact with no exact move …*) and its hop is not sent.
- **After a fight on the far side:** once the hop is under way the check does not stop it, but a fight ends the walk; if the lead bot is then more than 3 yd from the landing, the check runs again and the tighten walks back toward the foot. The way back up is one-way (the 2026-10-18 probe: a `cmd move` from the ramp to the foot ends at the ramp's edge, 5 yd short), so in practice it does not get the proof and the run pauses at the 36 s ceiling (no stand-in point, no hop sent from the ramp). Within 3 yd of the landing the hop counts as crossed and the run goes on.
- **Deployed together with its module:** the migration that writes these rows and the module that knows exact waypoints are deployed together and rolled back together; a newer DB under an older module is an unsupported state. The hop's row has a kind of its own, `move_hop_exact` (14 characters; `kind` is a varchar(16)), so such an older module does not send that hop: it ignores flag 64 and walks the foot as a plain move, and its loader skips the hop's row (`ai_dungeon_step: … (move_hop_exact) skipped (UnknownKind)` in the server log), so no direct order goes out for it. It then tries the next row (Wailing Caverns: seq 5, on the ramp below) as a plain navmesh move, which is **not guaranteed to be refused**: what that walk, or its 15 yd stand-in search, does from the ledge is untested. The run's status line shows the hop's kind as `move_direct` (`PlanStepKindName`).

`tools/test_dungeon_run_policy.cpp` (`TestExact*`, `TestDirectFromExactPointWaitsForTheProof`, `TestWalkBackReplaysTheExactPoint`) holds the Serpentis case: lead bot 2.3 yd from the foot, no direct order until the proof.

### Safety rules

From turtle-agent's remote driver (the same rules, now on the server):

- **Gather before a pull**, and pull only what is near: the nearest unit of the step, or of the next hop.
- **Never pull what a later step owns**: a unit near the next hop that a later `pull` or `boss` step lists (by entry, within its radius) is left for that step.
- **No unseen pack counted cleared, no live boss counted dead**: a pack or boss is judged only while the lead bot stands within 60 yd of it (its grid is loaded there), and only "no living unit left that is not friendly" ends it.
- **3 dead (or a wipe) regroup by itself**: once the fight is over. With 3 or more dead and someone still fighting, the run does not pause: the living fight on until the fight ends, and a fight that goes past the fight ceiling (180 s, a boss 420 s; also 420 s on any step with a plan boss engaged) with 3 or more dead is taken for the wipe it is and starts the regroup too (within the step's budget). A lead bot that dies first does not pause the run while the others fight; if they fall too, it is a wipe. The run revives the party (`cmd revive party`, as below), gathers it, and then **walks back** unless it stands on the last `move` point before the step, or within 30 yd of the step's own point and nearer to it than to that move point (a straight line from the entrance can be shorter to a pack than to its approach stand, with no path to the pack: Galgann pull 108 in the 2026-10-16 live run). With a `move_direct` point on the way (Uldaman's scorpid pit: every wipe strands the party at the entrance on the far side of it) it replays the plan's own points at once, from the one nearest the lead bot, since navmesh hops cannot cross the hole. Otherwise it goes first straight to the last `move` point before the step, in navmesh hops (at most 40), with the pull-before-move check at each hop, but only while the navmesh path read for each hop, its last leg included, keeps more than the group's radius plus 10 yd from every pull or boss group not cleared yet: the current and later ones, and earlier ones left uncleared (skipped, out of reach). The shortest way ignores packs and would body-pull them; only when that fails (no path, or the hops run out) does it replay the plan's own `move` and `move_direct` points in order, from the one nearest the lead bot (the instance entrance after a corpse run) up to the current step. Then it starts the step over. It is the way the run came. Each replayed point is walked as its `move` step is: a point more than 60 yd away (the party back at the entrance, a point beyond ReactDistance) is approached in navmesh hops as a resume does, and one with no path toward it at all is passed for the next; a hostile within 15 yd of it is pulled first (at most 8 such pulls in a walk back, counted apart from the step's 20, then pause) (a pack of a step already done that came back; the current step's own pack and later ones are left to their steps); a point refused now because it cannot be walked to (`unreachable`, `off-mesh`, `no-ground`, `no-los`) is passed for the next one, while a refusal for the lead bot's state of the moment (`lead-unavailable`, `busy` and the like) sends the same point again, at most 3 times, then pauses; and a party that came back near the step walks nothing. At most **2** regroups by itself per step; the third pauses the run as before (*3 dead: regroup (cmd revive party), then .bot run resume*). A dead lead bot alone (fewer than 3 dead) no longer pauses: see the wait rule below. Each wipe (the whole party dead) and each near wipe (3 or more dead, someone still alive) is counted once (a near wipe that ends in a wipe counts as both); the counts are in the regroup's note (*5 dead (2 wipes, 1 near wipe this run): regrouping by itself (1 of 2 at this step)*) and in the end note (*plan done (2 wipes, 1 near wipe)*).
- **The party waits for a fallen member until it is back** (the owner's rule of 2026-10-17: *"Party should wait if a party member dies until it is back."*). Every bot seen dead (the lead bot too; one that died in a walk; one that released, revived at the entrance and runs back) is remembered until it is alive again and within 20 yd of the lead bot. Once no living bot is in a fight, the run starts no pull, boss, task or move while one of them is not back: it starts the regroup (a resurrection in the party first, then `cmd revive party`, the gather, a stuck straggler summoned at the gather's ceiling, then a pause with the reason), and the step starts over from its beginning afterwards. Status: *waiting for Priest (dead), Mage (running back)*. The pull itself checks it too: no `pullback` goes out while a bot is dead (Uldaman rerun 19z11: 17 of 63 pulls went out with a member dead, 15 of them with the healer, among them the Sentinel pull 48 and Galgann, and two of the four wipes followed). A dead lead bot is revived by the regroup like any other bot and the walk back follows (it comes back at the entrance after a release); such a regroup counts against the step's 2 regroups by itself, and the third pauses (*the lead bot is dead: revive it, then .bot run resume*). Exceptions: inside a scripted event (a hold, its ritual or start step, the moves up to it: it cannot be left mid-way, the wait comes once it is over), while an object task or wait runs, while a member runs back with attackers (below), and a player's order (it pauses the run). **Fight first**: the regroup neither revives, gathers nor walks while a living bot is in a fight (Uldaman 01:43 and 02:31: three revived at the entrance while the two rogues still fought deep inside); deaths in that fight that make 3 dead hand over to the wipe regroup.
- **The lead bot back at the entrance alone** (Uldaman 19z11 02:48: the tank died alone, its own release and corpse run put it at the entrance within seconds while the others won the fight, and the step went on approaching the pack from there and paused at the scorpid pit). A lead bot that died in a fight and is back on its feet more than 60 yd from where it fell (by itself before the fight ended, or through the wait rule's regroup when the fight ended with it still a ghost: the hold is then filled the moment it is up, before the regroup gathers) is the wipe recovery: the regroup (the bots revived with it gather on it), then the walk back over the plan's own points and direct steps. The living party deep inside is not dragged back to the entrance: every living bot more than 20 yd from the lead bot and within 60 yd of where it fell is **held** on stay at its own spot (again after each run order), left out of the run's gathers, gather ceilings and summons, and follows the lead bot again once it comes within 20 yd, when the walk back ends, on a pause (the lead bot off the plan's map, a ceiling) or `stop`; after a player's order the bots are only let go (the order owns their movement). `cmd summon` brings a bot to the lead bot only (the lead bot is the summon point), so bringing the revived few to the party by summon would need a new summon target; the walk back is the existing, proven way. Counted against the step's 2 regroups by itself; the third pauses. A lead bot raised where it fell needs nothing.
- **Every regroup**: with a living priest, paladin or shaman out of combat, it waits 15 s for a resurrection in the party before `cmd revive party` releases the dead.
- **The rez hold** (`AiPlayerbot.DungeonRunRezHold = 1`, default `0`, which keeps the 15 s above): the regroup holds for the resurrection instead of 15 s. The run sends the resurrector no order. The bots' own AI picks who raises whom (and a resurrector short of mana drinks by itself); the status note names the one the run expects and how far it stands from the body and whether it sees it (*a resurrection in the party first (waiting for a resurrection: Holysis for Magnus, Holysis 21.4 yd from the body, sight no)*). One order does go out: when the hold has gone 12 s with a resurrector able and no cast or request under way, and the body lies more than 8 yd from the lead bot, the lead bot walks onto the body once per regroup (the party follows it into the resurrector's reach and sight; Uldaman 2026-10-20: a priest 15-24 yd from the body never cast in 63 s). While anyone is dead the run asks each second whether a resurrection can come: a living priest (Resurrection), paladin (Redemption) or shaman (Ancestral Spirit) that knows the spell, is out of combat and has the mana; a druid's Rebirth only when no living priest, paladin or shaman is on the map within sight, and only off its category cooldown and with its seed in the bags. It holds up to 60 s from the moment a resurrector could act (a wait for mana before that does not use the 60 s up), 12 s more for each body beyond the resurrectors, 120 s at most, and a resurrection already being cast or waiting to be accepted may finish (12 s more, once). It waits at most 90 s in all for a resurrector short of the spell's mana (*the resurrector drinks first*). It sends `cmd revive party` at once when nobody alive can resurrect or every body lies over 80 yd from the party, and when the time is up. The 240 s budget for the dead to be up after `revive party` starts when the hold gives up, so a long hold does not shorten the corpse run. A priest that raised the mage in 57 s (RFC 2026-10-20) is no longer released after 15 s. After Uldaman r4-19z21 (2026-10-21: the module refused the walk to a body on a ledge the navmesh does not join, "unreachable", and the run paused for a human), a path refusal of that walk (unreachable, off-mesh, no-ground, no-los) ended the hold at once and `revive party` went out, with the revived bot summoned to the lead bot as in any regroup; another refusal (busy and the like) only put a note on the status and kept the hold. The wipe (everyone dead) is unchanged. Derived from jrad7/mod-dungeon-clear's post-combat rez decision (AGPL-3.0-or-later).
- **A revived bot is summoned, not walked back** (every regroup: the wipe recovery, the wait rule's 1-2 dead, the lead bot's death, a resume). A fallen bot that is alive again more than 40 yd from the lead bot (or more than 8 yd above or below it), out of combat and with no attackers, gets `cmd summon <bot>` on the first tick it is so, before its corpse run takes it through the dungeon (the farthest first, one a tick, while others are still dead too); once per bot per revive (a bot that dies again and is revived again gets another). Never while it is in combat (`cmd summon` refuses that; a bot with attackers runs back to the party instead, below), never with the lead bot dead (it is the summon point), never a held bot. The regroup's gather waits until each summon has brought its bot within 20 yd of the lead bot; a summon refused, or not there within **10 s** (the summon takes 3 s), falls back to the walk-back: the bot walks in with the gather (a gather already out starts its ceiling over). A bot revived near the lead bot (a resurrection in the party) needs none. A `cmd summon` by hand right after each was alive, before the bats, had both at the altar within 20 s; one sent while they fought the bats did nothing. A fight during a regroup (a pack met on the corpse run) is handled as any fight (fight ceiling, kill-first focus, crowd control, event count); deaths in it that make 3 dead start the regroup by itself.
- **`.bot run resume`** (or `skip` from a pause) first **regroups**: `cmd revive party` while anyone is dead (again every 60 s; 240 s at most; a released lead bot whose ghost is outside the instance meanwhile does not pause it), then the party gathers on the lead bot (60 s, or the time the farthest bot needs at 3 yd/s when that is longer, at most 180 s: a revived bot whose summon failed walks the whole way; a bot whose summon is on its way does not count against it); a lead bot far from the step (back from the entrance) walks back as after a regroup by itself (straight to the last plan point in hops, else the replay). A resume gives the step its 2 regroups by itself back.
- **A gather goes back to the run's anchor** (the last point the run itself walked the party to: a move, an approach hop, a stand point; after a stalled arrival short of a point, where the lead bot stopped) when a fight left the lead bot off it: more than 8 yd above or below it (a tank that chased over a ridge) or with no navmesh path back. The lead bot then walks back to the anchor and the party gathers there; no pull goes out while the lead bot is still off it. On the anchor's floor with a path back, the gather stays on the lead bot's own spot. After a regroup there is no anchor until the run walks again. An approach hop the pack comes in sight during is walked to its end first (unless a unit of the step stands within 20 yd of the lead bot: then the hop is over and the pull goes out from where the lead bot stands, with the gather and the gather back left out for that pull only: combat, a regroup, a reset or another target ends it), and its end point becomes the anchor: breaking the hop off for the gather while the anchor was still the previous stand, more than 8 yd above, walked the party back up and the next hop forward again (Ragefire 19z13, trogg cave pull 13: eight hops, then the pause).

### Aggro estimate

Opt-in (`AiPlayerbot.DungeonRunAggroEstimate = 1`, default `0`; the ceiling is `AiPlayerbot.DungeonRunAggroCeiling`, default 6). Before each `pull` step's pullback the run leader counts the creatures the core would wake with the pulled one (`ai/playerbot/PullAggroEstimatePolicy.h`, derived from jrad7/mod-dungeon-clear's aggro-count estimate): the pulled creature's whole pack (`creature_groups` that aggro together, `creature_linking`), every creature whose aggro radius reaches the lead bot's firing spot (detection range, level difference to the lowest party member, line of sight from the creature to that spot, 3 yd of drift) and one ring of same-faction family assistance (10 yd). More joiners than the ceiling: the status note reads `N joiners expected` and the party rests to its end lines once for that pull (the existing rest wait, at most 60 s; a scripted event never rests), then the pull goes out. Such a rest is not counted toward the step's 300 s idle ceiling, and there are at most three a step: later pulls of the step go out without one, with the note `N joiners expected, rest budget used`. It adds no movement and never skips a pull; off, the run leader behaves exactly as before. It is related to the "tank does not hold threat" reports (turtle-agent#265, a second pack joining a pull) but does not fix the threat order itself. The pull's order line carries the count as well: a run with the ceiling on ends its pull status line with `N joiners expected` (the count read for that unit), or `joiners not read` when the estimate has not judged that unit this step.

**The estimate is approximate and can be high or low.** High: the drift widens every radius, and an assist needs the caller to see the assisted creature while only the pulled creature's sight of it is read. Low: the call-for-help chain a dragged creature makes along the walk back, a patrol that is elsewhere when the pull lands (the note then adds `(a patrol is the cause)` when the patrol alone puts it over the ceiling), auras that change an aggro radius, different but friendly faction templates, and pack members outside the 40 yd the scan reads beyond the step are not modelled. Cost: the sight reads are raycasts, only for creatures that could change the answer, for every unit of the step that has not had its rest yet, once a second while the run waits at a pull step (roughly 300 a second in a dense room).

### Pull stand

Opt-in (`AiPlayerbot.DungeonRunPullStand = 1`, default `0`; not yet proven in a live run). It covers a tank whose pull is a ranged weapon shot (bow, crossbow, gun, thrown weapon or wand). A spell pull, a body pull and a shot range of 5 yd or less are ordered as before. The run leader orders `pullback` only when the tank can shoot from where it stands: the target in the tank's sight, within its shot's own range (`PullStrategy::GetRange`, about 29.5 yd for a bow) less 5 yd, and the tank standing still (a moving tank is waited for up to 3 s, again after each walk). Otherwise the note reads `reading a firing stand for <entry> <guid>`, and on the next tick the party walks to a firing stand on the tank's navmesh path to the target (the path walked back from the target to the first point in range that sees it; for a target in range but out of sight, the first point of the path nearer it that sees it), at most 2 stands per target and step, then the order goes out. A stand walk that gains no ground for 12 s or lasts over 36 s is given up, and the order goes out from where the tank is (`firing stand unreachable: ordering from here`); the run never pauses for a stand, and the way back is checked first (a tank stuck on another floor gathers back before the order). A fight, gather or regroup in between ends the wait; the stands already walked stay counted for that target in that step. In the Wailing Caverns runs of 2026-10-21 (19z17) a tank ordered from a spot it could not shoot from walked to a firing position by itself and never fired from there (0 shots in 33 such pulls; 16 of 16 fired when the tank stood in range and sight), and the same order came again every 26 s. No stand found, the stands used up, or a scripted event: the order as before. Among units of the same kill-first rank one the tank can shoot from where it stands goes first. Each order's note names the target's guid, the how-many-th order to it this step and how its shot stood (`pulling 3636 0x... (order 2; shot from firing stand 1)`), so a re-order shows in the status line too. Off, nothing is read and the run leader behaves exactly as before. It does not fix the tank's own pull at its firing position (a separate fix in the pull action).

**A big pack's stand walk waits for the party** (Uldaman r10-19z29 step 79: the scorpid pack 7405 with 9 joiners expected; the stand walk was driven only on the ticks the stand rule ran, and on the ticks between, another scorpid's joiner rest and a read of the way back, the tank walked on unwatched to a stand 10 yd from the pack while the healer and the mage were 27-30 yd behind on the ramp; the pack woke on the warlock, the tank died with the priest at full mana out of range). From that fix on, a stand walk for a pull with 8 or more joiners expected (`kBigPackJoiners`; the count the aggro estimate read for that unit this step, so it needed `AiPlayerbot.DungeonRunAggroEstimate` on) was watched on every out-of-combat tick: a living bot more than 20 yd from both the tank and the stand stopped the tank where it stood (a gather on its own spot) with the note `big pack (N joiners expected, 8 or more): the firing stand walk waits for the party (<bot> <yd> yd behind)`, and the walk went on to the same stand once every bot was that close (`... the party gathered, on to the firing stand`). After 30 s it went on anyway (`... the party did not gather within 30 s (...): proceeding anyway`), and did not hold again on that walk. A pull with fewer joiners expected walked as before.

### Events

A scripted event is two or more steps: a **start** (`ritual`, or an `open` / `use_item` / `gossip` / `use_on` when an object, an item or an NPC's words start it), then a **hold**. The hold:

1. Walks the party to its spot (navmesh hops while it is out of sight).
2. Stands there. The run sends no pull of its own: the bots fight what the event sends with their own combat AI. After a fight that took the lead bot more than 8 yd off the spot, the party walks back to it (the bots chase in a fight; the run brings them back). An awake unit of the event (in `entries`, within `radius`, hostile) that has not come for 10 s is pulled.
   **The party's places**: the lead bot (the tank) holds the spot itself, the melee follow it, and every ranged bot and healer is walked to a stand point of its own and held there on `stay`: in a row 6 yd behind the spot, 3 yd apart across the line, on the side away from the event's mobs (the middle of the hold's first entry's units: the Stone Keepers, Archaedas; else of its awake ones; with their middle less than 5 yd off the spot, as the four Stone Keepers that ring theirs, the side whose row stands nowhere nearer to one of them than the spot does, since the script wakes each keeper onto the nearest player; with no such side, as at the Keepers, the ranged stand on the tank's own spot; no unit seen at all: the side the party came from, the nearest earlier `move` point), never more than 10 yd from the spot nor outside the hold's `radius`. A stand point the bot has no navmesh path to, or off the ground, is the lead bot's own spot instead. The places are set when the party first stands on the spot, again when the living party changes (a revived bot), and after a run move (the tank walked back, which forms every bot up on it) only for a bot more than 2 yd off its point; the held bots follow the lead bot again once the hold ends, on a pause or `stop`. Uldaman run 3 (19z12): with the party only following the tank, the priest and the mage stood 12-20 yd from it on the Keepers' spot and a keeper killed them there while the tank held `stay`.
   **The places are let go when the ranged fall out of the tank's reach** (Zul'Farrak r12-19z29 step 214, the pyramid event): the tank was sent alone at an event troll and chased it down the stairs while the four ranged bots stood on their places 36-60 yd off, and the freed crew at its side died to the trolls with only the tank beside them; in r8-19z26 a pull happened to open the second wave, its join released the places, the four followed the tank down and the crew lived. From that fix on, a hold's fight with the living lead bot (a tank) more than 8 yd (`kHoldReturnYd`) off the spot AND a living ranged bot or healer more than 30 yd (`kHoldFollowRangedYd`, measured on the ground: the 3D distance less the height) from the tank, for 2 fight ticks in a row (`kHoldFollowTicks`; a one-tick spike released nothing), cleared the places (`Run::holdStands`, a new generation, `holdPlaced` false, counted in `Run::holdReleases`, note *event: the tank is N yd off the spot, the ranged M yd behind the tank: the ranged leave their places and follow it (n)*), so the glue's release (`SyncHoldStands`, which forms the placed bots up on the lead bot) made them follow it. The tank's distance from the spot alone never released them: the Uldaman Keepers and Archaedas holds send the tank 15-20 yd after a keeper or a statue while the ranged keep their places 17-28 yd from it, in heal and cast range, which is what the places are for. A tank 35 yd out with the ranged still on their places was out of heal range, and there the places went by design. A dead lead bot kept them too (the rez and regroup rules apply). The release was one-way within the fight (the hold step does not run while the fight branch does): once the fight was over and the hold had walked the tank back to the spot, the places were set again, with a new generation, as on arrival. Nothing changed in the glue, the plan rows or the protocol.
3. Ends on its **done condition**, chosen by `flags`:
   - `8`: the instance script's data `entry` reads `param` (`InstanceData::GetData`, read once a tick, no world scan). With `32` that data is one of the core's encounter states (`EncounterState`: 0 not started, 1 in progress, 2 fail, 3 done): the event has **failed** when it reads 2, when it is back to 0 after it was seen started (a boss that reset and walked home), and when it does not leave 0 within 30 s of the hold (the start did not take).
   - `16`: the game object `entry` within 30 yd of the spot is in state `param` (as `wait_object`: `0` ready, `1` active, `2` active_alt). The lookup is `FindEntryTarget` with `kEntryPointRadius` = 30 yd from the step's point, a plain 3D distance and no object size, and the object must also be within the lead bot's reach: a spot farther than 30 yd from its object reads no state at all and the hold can never end (Dire Maul West r39 slot6 step 491: the crystal at -130.415 712.951 was 30.17 yd from the -150 690 spot).
   - neither: every unit of `entries` within `radius` is dead, after one was seen awake.

     Until 2026-10-22 only a tick outside a fight marked such a hold started, so a crew that turned hostile and was in the fight on the same tick never did: in Zul'Farrak r14-19z32 (slot 2, leg bly) Sergeant Bly, Oro and Raven turned 10 s after the gossip, died in that fight ("3 of 3 down"), and the hold paused twice with *event not done after 300 s (3 of 3 down)*. Since then an awake unit seen in the hold's fight marks it started too; holds with flag 8 or 16 kept their own start rule. Murta Grimgut (7608, the hold's second entry), who died 69 yd off and was never in the radius, did not hold it up: the rule never waited for an entry it did not see. The same review found the case of a fight that began on the hold's first tick, before the run had held the spot (a crew hostile at once): the event was not on, the fight was not counted and the hold waited to `timeout_s`; since then such a fight puts a hold done by its units on (only an awake unit starts it), and holds with flag 8 or 16 were left as they were.

     **All units dead before the hold** (Zul'Farrak r12 and r15-19z33, leg bly): the pyramid event's troll waves killed Bly's crew before the leg, so the hold stood on the spot with *4 of 4 down*, nothing alive and no unit ever awake, and ran its whole 300 s to the pause *event not done after 300 s*. Since 2026-10-22 such a hold ends 10 s (`kHoldAllDeadMs`) after the first look at the spot, on a tick with the spot in sight (the 10 s keeps running while the spot is out of sight), note *event done: none of its units is alive (they died before the hold)*, when no unit of it stood alive in the radius at any tick of this hold (`Run::holdUnitSeen`, friendly ones count), none was seen awake, and corpses of its units are in sight (*N of N down*, N above 0). Units that are only not spawned or not visible yet show no corpses and keep the 300 s ceiling, as does every hold with a unit alive; a hold that already started keeps the rule above (it ends at once when every unit is dead), and holds with flag 8 or 16 are not touched by this rule at all. Limits: the rule reads the hold's units in the radius only, and one corpse of a listed unit is enough (*N above 0*), not all of them. After a regroup the hold's flags reset (`ResetStep`), so a hold may end 10 s after the next look when one crew corpse lies in the radius and the live crew stands outside it; a dead Bly cannot turn his crew, and Bly's is the only units hold without a done flag, so this was accepted. The hold ends on the corpses of its listed units only. When Sergeant Bly lay dead and part of his crew was still alive and friendly, no unit had been seen awake, so the hold did not start: the 10 s rule needs every unit dead, and the run paused after 300 s.

   The instance data (`8`) and the object state (`16`, when the object is within the lead bot's reach) are read on **every tick**, with the spot in sight or not: in a fight, a rest, a regroup, a walk back or an approach the hold ends the moment its event is done. **A paused run** whose current step is a hold reads it too: once the event is done the step ends and the run resumes by itself, with a resume's regroup (revive, gather, walk back), note *event done: data 2 reads 3 while paused (...): resumed by itself, regrouping*; a run paused by a player (an order to the party, or `.bot run pause`) stays paused (*player order (...): ...; event done: data 2 reads 3 meanwhile: .bot run resume goes on with step N*). Uldaman run 3 (19z12): Archaedas died 12 s after the lead bot; the hold rested, then hopped toward its spot from where the lead bot came back to life, paused after 8 hops, and the agent's 10-minute pause cap ended the run FAILED with data 2 at 3 (done) and the vault door open.
   **The lead bot falls in a hold**: once the fight is over with the event not done and the lead bot dead (or back on its feet after it died there), the run regroups as the wait rule does (a resurrection in the party, `cmd revive party`, the gather or the held party, the walk back) instead of hopping toward the spot from wherever the lead bot is; the hold then goes on, or finds the reset and fails as below. A fallen member other than the lead bot is still waited for once the event is over.
4. Is bounded by `timeout_s` (fights included; a fight in a hold may last that long, not just 180 s): then it pauses (*event not done after N s*); `resume` waits again, `skip` goes on.
5. **The tank fights the event where it stands, inside the hold's radius.** A bot on `stay` does not fight at all (its attack actions are movement actions, which `stay` turns off: it only taunts), so in the hold's fight, while the lead bot is a tank on `stay` within the hold's radius of the spot and an awake unit of the event is in the fight (hostile, in combat, within the radius; never a dormant statue), the run sends `cmd attack <guid> <tank>` on one, which ends its stay: the healer's attacker first, then one on another member, then one on the tank itself, each the nearest. Once a hold order has taken it off its stay this fight, its own AI fights and the run sends it only at a unit nobody holds: never one already on the tank or the one it was sent at last, and while the tank holds a unit (one on it, or a mob hitting it in melee reach) only one hitting the healer, because each switch costs the threat it built (with Archaedas and a statue waking every 10 s, a "the one it is not on" rule sent it back and forth every 2 s). The guard keeps picking up. The party guard (above) runs in the hold too, with its own rules (in melee reach or casting, a mob on a healer at once, the tank's own mob in melee reach first), but only for mobs within the hold's radius of the spot, so no pick-up leads the tank out of the hold area. At most 3 orders per unit of the event (the count starts over each time one dies: a hold is one long fight), 2 s apart. Out of the fight the hold puts the tank back on the spot (`cmd move` to it, which puts it on `stay` there again), also when the fight left it on the spot. Uldaman run 3 (19z12) Keepers attempt 1: the tank stood on `stay` at 102 270 the whole fight without a target (*select new target* failed 1871 times in 100 s), a keeper killed the priest at 119 266, 17 yd away, the mage fled at 16 %.

An event may start fighting before its hold: the first Stone Keeper wakes with the ritual's cast. A fight while the current step is a start (`ritual`, `open`, `use_item`) or a move with only moves between it and a hold is the event's: it is bounded by the hold's timeout, not 180 s, and a ritual that answered ACK hands over to the hold at once. So does one that answered ERR `interrupted` while the hold's encounter data reads in progress (a safety net: the altar going back to ready as the keepers wake is the event starting, and the module's settle checks combat before the altar state; Uldaman run 4, 19z13).

Before a `ritual` whose hold reads an encounter state, the run looks at that data: already done, the ritual is left out; in progress or failed (a boss still walking home after a reset), it waits up to 60 s for the reset before the ritual goes out (the Stone Keepers stay at fail for good, so there the wait runs out and the ritual goes). A retry refused because the altar is still active (`busy`, "already in progress": the core leaves a summoning ritual active after its last use, and nothing in the Uldaman scripts resets it) pauses with *the altar is spent; an instance reset is needed to retry the event* (unverified live).

A **failed event** never hangs: the run goes back to the start step (the nearest `ritual`, `open` or `use_item` before the hold, with only moves, rests and waits between) and pauses with the reason (*event failed (data 1 reads 2, fail: the encounter reset): .bot run resume regroups and starts it again at step N (ritual)*). A wipe in a hold regroups by itself as anywhere; the event's encounter is not done after it (the reset), so the regroup goes back to the event's **start step** at once and starts it again there, once per event per run (the note says *the event starts again at step N (ritual)*); a second wipe in the same event regroups and the hold then finds the reset and pauses as above, so it cannot loop. Waiting on the spot instead waits for an event nobody restarted: Uldaman events-5, the wipe at 01:38:23 was followed by a walk back to the hold step, a 30 s wait for data 2 to leave 0 and the pause at 01:45:12 (6.8 min; unattended that pause hits the module's 10 minute pause cap and the run ends FAILED).

A hold owns its event's units: no hop before it pulls them (as a later `pull` or `boss` step owns its pack). The status line's phase shows the event: `hold 1/4 down` between fights, `fight 1/4 down` in one (dead units of the event of all seen: the units of the hold's first entry, dormant ones too, and any other unit of its entries once it is awake or dead; the some fifty dormant statues of Archaedas's hall count only once they wake, so his hold starts at `0/1`, not `0/53`), the note says it in words (*event: fighting (1 of 4 down, 1 awake)*).

### Keys and doors

Some dungeon doors are locked. The plan lists each one with the key that opens it and, where it applies, the Lockpicking skill that opens it instead (`ai_dungeon_leg_need`). Who has to bring the key depends on who is in the party:

- **Bot-only run** (no real player): with `AiPlayerbot.DungeonRunGiveItems = 1` (default) every bot gets the keys at the start and gives them back when the run ends. You do nothing.
- **Run with you in the party** (default `AiPlayerbot.DungeonRunBotKeysForPlayers = 0`): bring the key yourself, or have a character whose Lockpicking reaches the value named. The start warns once, naming the key and the Lockpicking value, plus where to get the key when no bot carries it. At a locked door the bots stop and wait about 25 yd before it. Open it with the key or by picking the lock. The run goes on by itself once the door reads open; `.bot run resume` also works then. `.bot run skip` walks the party past a closed door by hand.
- **`AiPlayerbot.DungeonRunBotKeysForPlayers = 1`**: the bots carry the keys and open the doors for you, so you need no key of your own.

An optional leg whose item nobody carries (Zul'Farrak's Gahz'rilla leg without the Mallet of Zul'Farrak) is skipped with a note.

The lead bot says on `/s` what the run needs: at a locked door it asks for the key (`Does anyone have Shadowforge Key to open the door? ### Player-led runs

Owner decision 2026-10-23 (the hybrid mode, in force since 2026-10-25): a real player leads his own party and walks wherever he wants; the run leader follows where he stands and does the pulls, raid marks, crowd control, boss tactics, rests and revives. It never teleports or summons a player. On by default through the run leader: `AiPlayerbot.DungeonRunPlayerLed = 1` on top of `AiPlayerbot.DungeonSelfClear = 1` ([settings](../server/settings/dungeons-raids.md#aiplayerbotdungeonrunplayerled)). Built in slices from 2026-10-24 on (design: S1-S9); what each slice did:

- **Start and binding (S1):** `.bot run start [plan] [from ...] player [tank <Bot>]` from the player who led a party (not a raid) of up to five whose every bot was his to control (his own bots, his hires, his claims; another player's hire was refused); up to three other real players could be in it (owner 2026-10-23: 1 to 4 players, the rest bots). The start made its own binding of that party: the player stayed its leader and the bots kept following him (no follow target was changed and nothing formed up on the tank), and the named tank bot, else the first tank-role bot of the party, was the binding's lead bot, the run's puller. Because the group was bound, boss tactics were on. The binding stood while the player led the party; handing the lead to anybody released it (*the player no longer leads the party*) and the run with it, as did the tank leaving the party or a raid conversion. A start refused after the bind (no plan, the player not in the plan's dungeon, ...) released the binding again; `.bot run stop`, a run that was done and a config reload that switched the key off released it too. Plain `.bot run start` stayed bot-led, and `.bot run mode` named the mode. The refusal codes are in [commander](commands/commander.md#run-leader-bot-run).
- **The player's orders (S2):** they never paused a player-led run; only `.bot run pause` and `.bot run stop` did. Every order hook (`.bot action`, `.bot cmd`, and the leading player's whispers and party chat to his bots, which were bot orders as ever, unlike in a bot-led run with players in it) was classed by its word: a **move** order (`follow`, `stay`, `come`, `formation`, `flee`, `guard`, `move`) was obeyed while the run went on, and after `stay` the run held its next pull until `follow` or `come`; a **fight** order (`attack`, `pull`, `pullback`, `focus`, `cc`, `aoe`, `sap`, `taunt`, ...) was the player's pull, so a pull of the run's own that was still gathering or waiting for its fight went back to the step's start; a **control** order (`rest`, `release`, `revive`, `corpse run`, `summon`) and any other order were obeyed and noted. The status note said *your order (stay, move): obeyed, the run goes on*. Another player's orders kept the in-party rule (his whisper or `.bot action` to the run's bots was refused).
- **Which step, and no walks (S3, the policy):** the plan's order no longer drove the run; where the player stood did. Every tick out of a fight, a regroup and an event the run picked its step: (a) the open `pull` or `boss` step whose units the party fought (by entry, within the step's radius plus 15 yd of its point), so a pack the player pulled himself or that came to him was adopted, its kill_first and crowd control with it; else (b) the nearest open `pull` or `boss` step whose point lay within `AiPlayerbot.DungeonRunPlayerLedPullYd` (40 yd) of the player in a straight line, on his floor (at most 15 yd above or below) and for the party's team; else nothing (idle: *next: pack (step 12, leg keystone), 52.0 yd NE (pulled when you stand within 40.0 yd of it)*). A step was done when the bot-led step machine ended it (cleared while seen, boss down, skipped, left out of reach); a set of done steps took the place of the forward cursor, the steps before a partway start counted as done, and the run ended (*every pack and boss of the plan is down*) only when no pull or boss step was open, not at the plan's last step. A picked pack whose pull was not out yet gave way to a pack the party fought; one the player walked more than 60 yd away from out of combat was dropped (left open). The pull went out only when the player had stood still for 2 s, every living bot stood within 20 yd of him (the gather waited and never walked anybody; the tank's own distance did not count), the tank saw the pack, his bots were not on his `stay`, and he was alive and in the dungeon (*pull ready: pack (step 4, leg 0), stand still to pull*); otherwise nothing went out and no idle time counted. A fight order of his held the run's pull for that tick. The run never walked: no `move` step, approach hop, walk back, anchor walk, gather walk, tank walk back to its guard stand, island hop or stranded-lead teleport went out (*not sent: move (you lead the way)*), and a `rest` was not sent while he walked. The pull, the rest gate, the crowd control marks, kill first, the fight ceilings, the regroup, revives and the wait for the fallen ran as in a bot-led run. The glue of this slice (reading where the player stands) came in S4.
- **The glue (S4):** once a second the run read the leading player (position, map, alive or a ghost, moving: more than 0.5 yd since the last read or his client's moving flag), the farthest living bot's distance from him, whether any bot or pet of the party was in combat, and the creatures in combat with him, his bots and their pets (their attacker lists, no grid search); then it picked the step and read that step's facts as before. The run's `pullback` anchored on the player (the tank pulled and came back to where he stood, as with `.bot action pullback`; the healer's stand was behind him), and `cmd summon` (a straggler, a revived bot) summoned the bot to him; both fell back to the tank while the player was dead, away from the tank's map, on a taxi or teleporting. Every form-up of the party (a hold's end, a task's end, the run's rest, `cmd follow`) made every bot, the tank too, follow the player with its own follow target; nobody was pointed at the tank or put on stay, and the tank was not put on stay for a rest. `.bot run skip` with no step picked left out the open pack or boss nearest the player. ### Cost

Nothing while no run exists. A running run ticks once a second (never per bot tick) and does at most one local grid search around its lead bot (a `boss` or `hold` step: one per listed entry), only when the step's point is within 60 yd. A `hold` done by data reads one instance data value a tick. It counts each bot's attackers from the core's attacker set (no scan). No database access after startup.
