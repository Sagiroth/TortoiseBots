# Configuration Knobs & Feature Flags

TortoiseBots provides a rich set of feature flags and tuning knobs. Whether you are running a solo private server or hosting a community realm, these settings allow you to customize bot intelligence, party convenience, world immersion, and economy.

Configuration lives in two installed files. The first install creates them from their templates (installed beside them as `.dist`); later installs never overwrite them, so compare with the `.dist` after an update to pick up new keys (a missing key uses its default):
1. `aiplayerbot.conf`, installed next to `mangosd.conf` — every `AiPlayerbot.*` gameplay flag, QoL toggle, AI threshold and service. Template: `ai/playerbot/aiplayerbot.conf.dist.in`. A different path can be set with `AiPlayerbot.ConfigFile` in `mangosd.conf`.
2. `modules/tortoise_bots.conf` in the server config directory — `TortoiseBots.*` module options (log level, telemetry). Template: `conf/tortoise_bots.conf.dist`.

Both are read once at server start; `.reload config` only re-applies `TortoiseBots.LogLevel`. A line that is commented out (`#`) in the template sets nothing — the code default listed below applies.

Listed today: Maraudon's Creeping Sludge (12222, aura 22638 Poison Shock, 180-220 nature every 2 s within 5 yd). On by default (owner decision 2026-10-15). |

### Per-tick AI pass budget (large pools)

The module's AI pass runs at the end of every world tick, so a bot a real player is playing with used to queue behind the whole random pool. Player-owned bots now always update first, every tick, and are never throttled; the random pool runs after them in a round-robin order that resumes where the previous tick stopped, so a bot that misses a pass is served on a later one and never dropped.

**Who counts as player-owned** (the rule is deliberately about real ownership, not bookkeeping flags):

- a bot whose master is a **live player with a network session** — hired companions and party bots while their player is online; and
- a bot on an account the random pool does **not** own (`tortoise_bots_pool_account`), i.e. the owner's own characters.

Everything else is the pool, including characters on `RNDBOT` pool accounts that carry a master from a bot-only group, a stale `PlayerMaster` lease, or `random = false` after a restart. Those flags are not ownership signals: bot-only groups hand their members a bot master and a lease (`PlayerbotAI::GetGroupMaster` → `BotManager::BindBotMaster`), which once misclassified ~40 % of a 500-bot pool (212 bots) as player-owned and kept them unbudgeted.

The pool runs as one turn queue under a per-tick time budget. After each turn a bot is due again when its AI asked to think next, never later than its situation allows (combat 400 ms, dead or in a battleground 1 s, mid-teleport 100 ms, anything else 3 s; combat means the core's combat flag or the bot AI's own combat state); a change of situation makes it due at once. Each tick the due bots run most overdue first relative to that cap until the budget is spent. On a healthy server the self-tuning controller below keeps the effective budgets at their ceilings; when ticks run long it shrinks them and every pool bot runs proportionally later, fights least.

| Setting | Default | What It Does |
| :--- | :---: | :--- |
| `AiPlayerbot.PoolTickBudgetUs` | `10000` | Ceiling for the pool turn queue, added to `CombatTickBudgetUs`: microseconds of module work per tick. `0` removes the budget entirely (every due bot runs). Values below `1000` are raised to `1000`; `100000` is the ceiling. |
| `AiPlayerbot.CombatTickBudgetUs` | `15000` | Second half of the same budget (it once fed a separate combat pass; the two now add up, so existing configs keep their total). `0` removes the budget entirely. |
| `AiPlayerbot.PoolBudgetWhenTickOverMs` | `0` | The gate: the budget applies only while the previous world tick took longer than this. `0` applies it on every tick — the default, because the self-tuning budget below reclaims the full ceiling on a healthy server by itself. |
| `AiPlayerbot.TargetWorldTickMs` | `100` | Self-tuning tick budget: each tick the controller moves the effective pool/combat budgets from the measured previous world tick so the tick stays near this target (over target + 10 ms: shrink fast; at or under: creep back +1 ms/tick; the world thread pads healthy ticks to ~50 ms, so reclaim keeps the full ceilings on a healthy server). It only cuts what it can win back: it shrinks when the tick is over target + 10 ms and the rest of the tick (core, other services, player-owned bots — everything but the pool turns) plus the 4 ms floor would fit under that line; when the rest alone keeps the tick over, it holds the budgets instead, because cutting bots there only makes them late. No hardware detection — a fast PC keeps the full ceilings, a weak one backs off on its own. `0` disables the controller (static ceilings; also set `PoolBudgetWhenTickOverMs=150` to restore the old gate). |

Tuning: on a healthy server you should not need to touch anything — the controller keeps the full ceilings while ticks stay under the target. If pool bots feel sluggish while the tick is long, raise `PoolTickBudgetUs` (e.g. `25000`–`50000`); if the world tick itself will not come down, lower `TargetWorldTickMs` -- but first read `coreMs` in the BOTPERF line: when it alone is near or over the target, cutting bots cannot bring the tick down, and a lower target only starves them. The target trades player lag for bot speed: measured on 2000 bots, `50` gave lag p95 66 ms with 14.5% of bots stalled, `100` gave 107 ms with 7.4% stalled. If the server cannot hold the target at all, run fewer bots. The budget is checked between bots, so a pass can overshoot by one bot's work. Player-owned bots always run first and unbudgeted, whatever the budgets say.
Tuning: on a healthy server you should not need to touch anything — the controller keeps the full ceilings while ticks stay under the target. If pool bots feel sluggish while the tick is long, raise `PoolTickBudgetUs` (e.g. `25000`–`50000`); the controller cuts the larger ceiling back only when the pool turns are what push the tick over target. If the world tick will not come down while the budgets sit at their ceilings, the time is going outside the bot pass (the core, see the `mangosd.conf` table below): lowering `TargetWorldTickMs` will not help there, lower the ceilings or run fewer bots instead. The target trades player lag for bot speed: measured on 2000 bots, `50` gave lag p95 66 ms with 14.5% of bots stalled, `100` gave 107 ms with 7.4% stalled. If the server cannot hold the target at all, run fewer bots. The budget is checked between bots, so a pass can overshoot by one bot's work. Player-owned bots always run first and unbudgeted, whatever the budgets say.

**Value cache refresh (experiment, off by default).** Bots read most of what they know (targets, inventory, quest and travel state, ...) through cached AI values, each with a check interval in seconds. The cache has always refreshed after half that interval in whole seconds (`now - lastCheck >= interval / 2`), so interval `2` refreshes every second, `5` every 2 s, `40` every 20 s, and interval `0`/`1` recalculates on every read.

| Setting | Default | What It Does |
| :--- | :---: | :--- |
| `AiPlayerbot.ValueRefreshAtInterval` | `0` | `1` refreshes a value with interval 2 or more after its full interval instead of half of it, which halves those recalculations. Values with interval `0`/`1` (health, mana, auras, targets, inventory and every other default-interval value) still recalculate on every read. The values that sense the fight keep the old half-interval rule: `attackers`, the attacker counts (`attackers count`, `my attackers count`, `has attackers`, `has agro`, `balance percentage`, `possible attack targets count`, `has possible attack targets`), `possible attack targets`, `possible targets` (and `all targets`, `nearest adds`), `nearest stealthed units`, `possible triggers`, `nearest damaging traps`, `boss target`, `aoe heal` and `has enemy players`; so do the free-move values `free move center`, `free move range` and `can free move` (a follower restarts when its master runs out of range, and heal-target, grind-target and possible-target filtering read the same centre) and `grind target`. Everything else (travel purpose, quest needs, vendor and repair checks, group members, estimated group DPS, ...) may react up to twice as late as today. Off by default because it is a behaviour change measured on one server so far; the code with it off is the old formula exactly. |

To A/B it, run the same pool size and bot mix twice, `0` then `1`, for at least 20 minutes each after the pool has settled, and compare the BOTPERF lines below: `usPerTurn` and `passUs` should drop, `turnLateAvgMs` should not rise. Then check behaviour that hangs on the slowed values: bots still pick grind targets and quest objectives, start vendor and repair trips, follow and join their group, and eat and drink between fights.

With AI enabled (`AiPlayerbot.Enabled = 1`), the module reports the pass once per ~30 s of world-tick time at `TortoiseBots.LogLevel = 1` or higher (default `2`):

```
TortoiseBots: BOTPERF passUs=812 playerBots=5 ownedBots=5 masterBots=0 poolBots=495 poolProcessed=4 due=9 budgetHit=1 maxUs=9820 ticks=62 poolBudgetUs=10000 combatBudgetUs=15000 turnLateAvgMs=180 turnLateMaxMs=1400 turns=410 usPerTurn=1900 coreMs=78 combatTurns=95 combatLateAvgMs=60 otherTurns=315 otherLateAvgMs=240
```


`passUs` is the average `UpdateBots` cost in the window in microseconds (`maxUs` the worst), `playerBots` the unbudgeted candidate count, split into `ownedBots` (owner's account) and `masterBots` (live player master), `poolBots` the pool candidate count, `poolProcessed` the pool turns that pass ran (a record that was unusable that tick still counts) out of `due` bots due, `budgetHit` `1` when the budget cut that pass short, `poolBudgetUs`/`combatBudgetUs` the effective budgets the pass just ran under (their sum is the one budget; equal to the configured ceilings when the server is healthy), and `turnLateAvgMs`/`turnLateMaxMs` how far past due the window's pool turns ran — the direct measure of how far behind the pool is. Appended for tuning the budget: `turns` the pool turns run in the window, `usPerTurn` the average microseconds one turn took (the turn loop's wall time divided by `turns`; capacity per tick is roughly the budget divided by this), `coreMs` the average world tick minus the average bot pass (the share of the tick the core and other services spend, which cutting bots cannot reduce), and `combatTurns`/`combatLateAvgMs` against `otherTurns`/`otherLateAvgMs` the turn count and average lateness split by the scheduler's situation (core combat versus everything else). Also appended: `routeReuse` counts the window's movement route lookups (`ResolveMovePath`) answered from the cached route (the old early reuse of the last long path, plus the travel route cache's hits), and `routeRebuild` counts the lookups that planned the route again (node-graph search or direct navmesh path; the expensive part). Both reset with the window. The sample above predates these two fields. Read it like this: `budgetHit=1` with a small `passUs` is the throttle working; `budgetHit=1` and `poolProcessed=1` means the budget is too tight for the pool size (raise it); a low `passUs…

### Server settings for many bots (`mangosd.conf`)

Hundreds of always-active bots keep most of both continents busy, which the core's defaults don't expect. These core settings matter most:

| Setting | Recommended | Why |
| :--- | :---: | :--- |
| `CleanupTerrain` | `0` | Keep terrain loaded. With `1` the core frees unused terrain every 60 s, and a bot that walks back into it reloads it inside its own turn: about 2 s freezes, even on a core with [#588](https://github.com/tortoise-wow/tortoise-wow/pull/588). `0` costs about 2 GB of RAM (the continents' terrain); see the note below the table. |
| `PlayerSave.Interval` | `300000` | The 60 s default saves every bot in the same minute; 5 min removes that write wave. A crash loses at most this much progress. |
| `DynamicRespawn.MaxReductionRate` / `DynamicRespawn.MinRespawnTime` | `0.75` / `15` | Speed up respawns where many players/bots crowd: the core shortens spawn timers near groups of players (defaults cap the cut at `0.25` and never below `25` s). On bot-heavy servers raise the cap and lower the floor so starter valleys and grind fields keep up with a crowded pool. Core defaults are `0.25` / `25`; the rest of the `DynamicRespawn.*` block stays at its defaults. |
| `LootsLogFile` / `CharLogFile` | `""` | To the core a bot is a player, so every bot loot and every bot login lands in `loot.log` / `char.log`. With 1000 bots `loot.log` gains about 450,000 lines (~50 MB) a day, and neither file is ever rotated. An empty file name turns the file off. |

**CleanupTerrain and the core fix.** The core frees unused terrain every 60 s. On a core without [#588](https://github.com/tortoise-wow/tortoise-wow/pull/588) (open upstream as of 2026-10-13), the test in `Map::LoadMapAndVMap` (`src/game/Maps/Map.cpp`) reads `m_bLoadedGrids[gx][gx]` instead of `[gx][gy]`, so an active grid never takes a terrain reference: the cleanup unloads tiles that bots stand on, and each reload stalls the map tick. #588 is that one-line fix. A core has it when the test reads `m_bLoadedGrids[gx][gy]`.

- **Core with #588:** still set `CleanupTerrain = 0`. #588 ends the stalls every minute, but freed terrain still has to be reloaded when a bot walks back into it. On a 1000-bot realm with #588 (2026-10-13), `1` gave three single-bot turns of 1.7–2.3 s in 35 minutes (lag p95 108 ms); `0` gave none (slowest bot turn 80 ms, lag p95 85 ms). Only use `1` on a machine that cannot spare about 2 GB of RAM.
- **Core without #588:** `CleanupTerrain = 0` matters even more, at a memory cost: the continents' terrain (about 2 GB extracted) stays loaded. On a 500-bot test realm it cut slow (>200 ms) map ticks from 126 to 20 per 10 minutes, together with `PlayerSave.Interval = 300000`. On a low-RAM machine keep `1` and accept the stalls.
- **Measured:** on the 500-bot test server with `CleanupTerrain` left at `1`, stalls of 2 s or more ran 120–124 per hour on build 18 (without #588). Build 19d, which has #588 applied, had none in about 72 minutes (09:00–10:12 on 2026-10-13).

Core PR [#586](https://github.com/tortoise-wow/tortoise-wow/pull/586) (open upstream as of 2026-10-13) is the other core-side tick fix: `ChannelBroadcaster` busy-spins and uses about 0.4 of a core; the PR makes it wait on a condition variable instead.

## 4. Combat & Reaction Thresholds

Fine-tune how aggressively bots heal, rest, or drink:

| Setting | Default | Tuning Guidance |
| :--- | :---: | :--- |
| `AiPlayerbot.CriticalHealth` | `20` | Percent health considered an emergency. Triggers *Lay on Hands*, *Last Stand*, *Shield Wall*, or *Divine Shield*. |
| `AiPlayerbot.LowHealth` | `50` | Percent health triggering prioritized heavy heals (*Greater Heal*, *Healing Wave*). Increase to `65` for safer dungeon runs. |
| `AiPlayerbot.MediumHealth` | `70` | Threshold for maintenance heals (*Renew*, *Rejuvenation*, *Flash Heal*). |
| `AiPlayerbot.AlmostFullHealth` | `90` | Health ceiling above which bots stop casting heals to conserve mana. |
| `AiPlayerbot.LowMana` | `15` | Mana floor where casters switch to low-cost wanding or conserve mana. |
| `AiPlayerbot.MediumMana` | `40` | Threshold where bots consider conservative rotations. |
| `AiPlayerbot.RandomBotCombatStrategies` | `+dps assist,-threat` | Strategy changes applied to every pool bot's combat set after the spec defaults (at login/reset and again on each periodic `AiPlayerbot.Min/MaxRandomBotChangeStrategyTime` refresh). Leave `+dps` out: for a priest `dps` is the Shadow spec, so it moves Holy and Discipline pool priests onto the Shadow rotation without the Shadow talents (they fill with *Smite*). A tank (Protection warrior/paladin, bear) keeps its `tank assist`: when this list's `+dps assist` swaps it out, it is put back. Grouped non-tank bots with a real-player master (outside battlegrounds) get `threat` added back after this list (unless the player turned it off), so `-threat` here only affects masterless pool bots. Bots with a saved strategy snapshot replay it instead until re-saved. |
| `AiPlayerbot.PoolMeleeHoldGround` | `0` | Opt-in. `1` = pool and free warriors and rogues get no generic `flee` combat strategy (`panic`, `outnumbered`, `critical health no master`), so they fight on with their own defensive kit instead of breaking off, like mod-playerbots melee. Other classes and bots with a real player master are unaffected. Takes effect after a server restart. |

## 5. In-Game Live Toggles (On the Fly via `/tbm` or Chat)

You do not need to restart the server to adjust tactical behavior during gameplay. You can toggle these anytime:

### Tactical Gameplay Toggles (`.bot action <toggle>`)
- `.bot action aoe <on|off>` — Enables or disables Area-of-Effect abilities (crucial around crowd-controlled mobs).
- `.bot action pull [seconds] [ranged]` — Tank pulls your target and stays fighting there; party DPS hold at your position for `seconds` (0-60, default `AiPlayerbot.PullDpsJoinDelay = 10`) after the pull lands. The addon advertises support via the `TBM:CAPS|pull-seconds` roster trailer. With `AiPlayerbot.RangedPull = 1` (default) the tank shoots instead of walking in when the mob is in sight and in shot range and unreachable by path or farther than `AiPlayerbot.RangedPullMeleeApproach` (20 yd); the word `ranged` asks for it on any pull.
- `.bot action pullback [seconds] [ranged]` — Tank pulls from range and returns to your position, holding there and picking the pulled mob up as it arrives; party DPS join `seconds` (0-60, default `AiPlayerbot.PullBackDpsJoinDelay = 5`) after the tank is back. The return leg is capped by `AiPlayerbot.PullBackMaxReturnTime = 15`.
- `.bot action focus` — Focuses party damage onto the mob marked with the Skull raid marker.
- `.bot action cc <mark>` — Assigns CC to a specific raid marker (e.g. Moon, Star).

### Strategy & Stance Toggles
Using `.bot strategy <change> [Name]` (change first, optional bot name second) or the `/tbm` addon:
- `.bot strategy +conserve mana` / `.bot strategy -conserve mana` — Restricts casters to basic, high-efficiency spells.
- `.bot strategy -cast time` / `.bot strategy +cast time` — On by default outside battlegrounds. Lifetime-aware: a cast aimed at the bot's current attack target is cut to x0.1 priority when its cast time (plus up to 3 s of channel) exceeds the target's estimated time to live, `target HP / estimated group dps` (the cached `estimated group dps` value: bot party members' level, role and gear score). Casters stop starting 3 s Frostbolts/Shadow Bolts on mobs that die first, while a boss at low health percent but with a long lifetime keeps getting full casts. Ground-targeted spells are exempt; an unknown estimate (dps 0) never vetoes. Heals aimed at party members never match the attack target and are not held back.
- `.bot strategy +loot` / `.bot strategy -loot` — Toggles whether bots run to loot corpses after combat.
- `.bot strategy +silent` / `.bot strategy -silent` — Silences bot chatter in party/say chat so they execute commands quietly.
- `.bot strategy -passive` — Halts all bot attacks; bots will only follow and hold fire.
- `.bot formation <arrow|line|circle|shield>` — Changes follow positioning around the leader.

## 6. Diagnostic Logging

The native module layer (bot lifecycle, random-bot, Auction House, battleground queue, and LFT services — everything under `host/` and `runtime/`) has its own verbosity setting, independent of the core server's own `LogLevel`. This lets you trace what the module is doing without turning on the engine's full debug output, and vice versa.

```ini
[TortoiseBotsConf]
TortoiseBots.LogLevel = 2
```

| Level | Name | Shows |
| :---: | :--- | :--- |
| `0` | Minimal | Errors only. |
| `1` | Basic | One-off startup, shutdown, and diagnostic test results (e.g. `PendingAddRemoveTest`, `AutoTest`), plus the periodic `BOTPERF` AI-pass cost line. |
| `2` | Detail (default) | Per-bot state transitions: session start/stop, add/remove, AH postings, BG queue entries. |
| `3` | Debug | Per-tick and per-packet traces. High volume — intended for short diagnostic sessions, not left on. |

Errors (`sLog.outError`) are always written regardless of this setting. The level is re-read on `.reload config`, so it can be raised or lowered without a server restart.

### Bot CSV files (`AiPlayerbot.AllowedLogFiles`)

`bot_events.csv` (bot decisions) and `deaths.csv` (bot deaths and killers) are written to the server's logs directory by default, so a bug report can include them. The live file is plain text. Every hour, and at server start, it is packed into `<name>_<date>_<time>.csv.gz` next to it, named after the time it was closed. Packs older than `AiPlayerbot.LogRetentionDays` (default `3`, `0` = never delete) are deleted. Packing runs in the background, and a server stopped in the middle of it packs the leftover file on its next start. Three days take roughly 65-130 MB at 500 bots and 130-260 MB at 1000 bots. An empty `AiPlayerbot.AllowedLogFiles` writes no bot log files at all. A log file that cannot be opened (for example the logs directory does not exist) is reported once and skipped for 5 minutes, then tried again (and reported again if it still fails). Other diagnostics (`travel_route_gate.csv`, `ghost_moves.csv`) are added to the same comma-separated list.

This setting is separate from the strategy AI's own action trace, which stays gated behind the `debug`/`debug action` bot strategies (`.bot strategy +debug`) rather than a server-wide config key.

### Action counts (live rotation measurement)

| Setting | Default | What It Does |
| :--- | :---: | :--- |
| `AiPlayerbot.ActionCountsLog` | `0` | When `1`, every executed bot action is counted by bot class id and action name (class `1` with `shield slam` is a warrior's Shield Slam; the report script prints class names), split into ok vs failed/impossible outcomes. Every 5 minutes a cumulative snapshot (`utc_time,class,action,ok_count,fail_count`) is appended to `logs/action_counts.csv`, next to `bot_events.csv`. `0` costs one branch per executed action and nothing else. Needs a restart. |

Turn it on for a measurement window on a busy realm, then copy the live file twice a while apart and diff the copies to see what each class actually spends its time doing:

```
cp logs/action_counts.csv /tmp/actions_early.csv
# ... wait 30+ minutes ...
cp logs/action_counts.csv /tmp/actions_late.csv
python3 tools/action_counts_report.py /tmp/actions_early.csv /tmp/actions_late.csv --top 10
```

A copy taken mid-dump can tear (the 5-minute append is not atomic): copy twice back-to-back and compare the two before trusting one — identical files mean a clean copy.

The report prints the top actions per class between the two snapshots with the ok share, so dead or failing actions (low ok share) stand out. Counters are cumulative since server start; comparing snapshots from different runs is meaningless.

## 7. Bot Chatter & Broadcasts

Flavor and status lines come from the `ai_playerbot_texts` table (seeded by
`data/sql/world/20260913090000_world.sql`). If bots speak raw keys such as
`quest_accepted`, that table is empty — re-apply the migration and restart.
Volume is controlled by these knobs (all need a restart):

| Setting | Default | What It Does |
| :--- | :---: | :--- |
| `AiPlayerbot.EnableBroadcasts` | `1` | Master switch. `0` disables all quest/loot/kill/level-up/suggest broadcasts. |
| `AiPlayerbot.BroadcastToWorldGlobalChance` / `BroadcastToGeneralGlobalChance` | `3000` | Main throttle on what reaches world/general chat (range `0`-`30000`). `0` re-routes most broadcasts away from that channel. |
| `AiPlayerbot.BroadcastChance*` | varies | Per-event chance, e.g. `BroadcastChanceQuestAccepted`. `0` disables that one class. The toxic lines (`*Toxic*`) and the trade spam (`BroadcastChanceSuggestSell`, the "WTS"/"I am selling" lines pool bots hawk in say/yell/trade/general) default to `0`; the Thunderfury joke defaults to `1` — set `AiPlayerbot.BroadcastChanceSuggestThunderfury = 0` to silence it. |

Travel picks ("Traveling 123y to ...") and vendor confirmations ("Selling ...") are silent unless a live player asked: a direct `.bot`/`go`/`where` command reply still answers its requester, but autonomous pool-bot narration and bot-to-bot trade/enchant lines (RPG "You can use this ..." / "Let me enchant this ..." between two bots) never reach chat.

### Previous-run bot logs

Enabled logs opened in write mode (including `bot_events.csv` and startup
travel/pathfinding dumps) retain the previous file as `<filename>.1`. Rotation
happens once per filename per process; later dump refreshes leave that backup
alone. Append-only logs retain their existing behavior. No CSV columns change.
If rotation fails, the truncating open is refused and an error is logged; later
ordinary log writes may append to the preserved current file. Disabled logs
are not touched. Keep copies elsewhere if more than one previous run is needed.
