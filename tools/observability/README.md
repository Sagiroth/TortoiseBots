# Observability daemon — developer notes

`tools/observability` is a standalone Go daemon (Prometheus + web dashboard) fed by `runtime/ObservabilityEmitter.{h,cpp}` over non-blocking UDP. It is optional and config-gated; core stays ignorant of it.

Rules that keep its state honest:

- The daemon has exactly one authoritative store (`internal/state`). REST, WebSocket, and Prometheus all read it.
- The emitter sends self-contained snapshot cycles: one `HEARTBEAT` + `BOT_BATCH` chunks sharing a `seq`. Publish a roster only from a complete cycle; clients replace their roster wholesale instead of merging deltas.
- Player lag: the heartbeat carries `lag_p50`/`lag_p95` (Prometheus `mangos_player_lag_p50_ms`/`_p95_ms`): how long a player's action waits before the server handles it, from the world-tick lengths of the last 30 s. An action lands in a tick with probability proportional to its length and waits for the rest of it (`runtime/PlayerLagWindow.h`). Against a headless probe client at 2000 bots it read about 15 ms under the measured p50/p95 (the time into the next tick before the player's map is processed is not modelled). This is the server's share of what a player feels; their ping comes on top, and the in-game latency meter never includes it (the core answers `CMSG_PING` on the network thread). `diff_avg`/`diff_worst` are the plain mean and worst tick of the same window.
- Every datagram also carries a `session` epoch (server process start). The daemon resets sequence/roster state when it changes, so a server restart that resets `seq` cannot be locked out as "old cycles".
- Bound and prune every emitter table (bot tracking, action failures, anomaly cooldowns) on each snapshot. Macro-state ratios are windowed, never lifetime totals.
- Anomaly types are a closed set (`model.AcceptedAnomalyTypes`) so Prometheus label cardinality stays bounded.
- `SERVER_INFO`'s `bots` object mixes numbers (pool sizes, intervals, budgets) with `"0"`/`"1"` flag strings: `ServerInfoPayload.Bots` is `map[string]any`. Typing it as `map[string]string` made `encoding/json` reject the whole datagram (silently, via the listener's error return), which left the Server panel and diagnostic report permanently empty.
- Add a datagram type to the daemon's `processPacket` switch: an unknown type falls to the anomaly parser and is dropped, which is also what an older daemon does with `COMMANDERS`.
- Bump `kProtocolVersion` in `ObservabilityEmitter.cpp` and `model.ProtocolVersion` in `internal/model/types.go` together. New `BOT_BATCH` fields are additive (`omitempty`): an older module simply omits them and the daemon reads the zero value.

**Forwarding (issue #273).** The daemon's `-forward-udp` flag (comma-separated `host:port`, empty by default) copies every received telemetry datagram, byte for byte and before it is processed, to each extra address, so a second dashboard can run beside the owner's without taking the only target. Each copy has a 50 ms write deadline; a failing target is logged at most once per 30 s and never stops or delays the listener. The same list can be set with the `FORWARD_UDP` environment variable (the flag wins). Start-up refuses a target that would loop the daemon's input back into itself: an unspecified address (`0.0.0.0` or `::`), the exact listen `ip:port`, and, when listening on the wildcard, the same port on a loopback or any local interface address. As a second guard, a datagram whose source is one of the daemon's own forward sockets is dropped (neither forwarded nor processed), which catches a same-host loop however the target was spelled. Limits: forwarding ran on the read loop with a 50 ms write deadline per target, so at most 4 targets are accepted (a fifth is refused at start-up) and at most 200 ms is added to one datagram when every target blocks. Loops through another daemon (A forwards to B and B forwards to A), through NAT or through a docker bridge address were not detected; never forward to anything that forwards back. Targets were resolved once at start-up, so a host name that changes address needs a restart. The sockets are closed by `Listener.Stop`. The logic is in `internal/udp/forward.go`, tested in `internal/udp/forward_test.go`.

## Telemetry surface (protocol v12)

Each `BOT_BATCH` bot entry carries: `name, guid, player, alt, kind, group, guild, class, role, level, xp, next_xp, hp/max_hp, power/max_power, power_type, map, zone, instance, subgroup, x/y/z/o, target, target_level, strategy, state, last_action, last_trigger, travel_purpose, travel_to, travel_status, travel_dist, ai_visits, ai_age_ms`. `kind` is the dashboard kind label (issue #872): pool, hired, claimed, alt (autonomous owned alt-bot), companion (owned alt following its player), player. A pre-v11 module sends no kind and the daemon backfills pool/player/alt from the flags. Pool KPIs (grinding rollup, level bands, level timeline) exclude player and alt rows like before. `guild` is the guild name read from the in-memory guild manager on the snapshot (no database reads, which would stall the game server); it is additive, so an older module omits it and the row reads guildless. The Bots tab shows it as the **Guild** column (sortable, filterable via `guild:name`) and in the bot detail view, with a dash when the bot is in no guild.

`instance` and `subgroup` (v12, issue #895) place a unit inside an instance copy: `instance` is the core's `Map::GetInstanceId()` (0 in the open world, non-zero in a dungeon, raid or battleground copy; `subgroup` is the unit's raid subgroup). They are additive: a pre-v12 module omits them and the daemon reads no instance — the Dungeons tab then falls back to one run per map (it cannot tell copies apart) and says so.

Real players ride the same snapshot cycle as bots: the emitter collects online network sessions (`HasNetworkTransport`, the same predicate behind the heartbeat `humans` count) every 2 s snapshot and appends one row per player with `player: true` and `group` = core group id (0 = solo). Bot-only detail stays empty (no role/strategy/AI age/travel); state is the visible unit state (combat/moving/resting/dead/idle). The daemon stores them in the same roster (list/map/profile join by guid) but excludes them from pool KPIs (grinding rollup, level bands), issue episodes, the level timeline and the class/role census; trails are bot-only. The Bots tab has a Bots + players / Bots / Players filter plus kind chips (pool/hired/claimed/alt/companion/player/own), every row carries its kind badge, map markers are rings in the class colour, tooltips and the profile show group instead of the AI role, and the profile skips the database subtabs (players are not pool bots). Heartbeat `humans` counts the same player rows the batches deliver; `bots` counts bot rows only.

`zone` (snapshot and event rows) is the zone the core caches on the bot (`GetCachedZoneId()`), not a terrain lookup. The core sets it at login and teleport and refreshes it on its one-second zone update, so at a zone border it can trail the bot's position by up to one second. Where the terrain has no area row, the cache keeps the last real zone instead of reporting 0.

Macro states (`state`, heartbeat `states`, `tortoisebots_state_ratio`): `combat` (in combat), `moving` (a movement generator owns the bot), `busy` (standing still but doing real work: looting, casting, sitting to eat/drink, movement within the last 45 s, or a fight/XP gain within the last 60 s), `stalled` (standing still for 45+ s whose only activity was churn — an active travel target or a changing last-action name, no movement/loot/cast/sit and no fight or XP gain in the last 60 s — i.e. standing with a destination and getting nowhere), `resting` (rest flag), `idle` (no movement, action, cast, loot, or active target for 45+ s — really doing nothing), `dead`. `stalled` exists so a bot parked with a travel target is no longer reported as busy. Per-tick cost is member reads + one action-name compare; the 3-min window is unchanged.
- `power_type` is the current resource (`mana`, `rage`, `energy`, `focus`, `happiness`); druids reflect their active form. Label bars by it, never hardcode "mana".
- `last_trigger` is the trigger that led to `last_action` (both are stored per engine state and change together, only when an action succeeds); failed or skipped attempts leave the pair untouched.
- `last_action`/`last_trigger` feed repeated-action detection; they are sampled per 2s snapshot, not per execution.
- Anomalies carry `guid` so the daemon can key episodes; accepted types are `STUCK`, `ACTION_LOOP`, `UNREACHABLE_TARGET`, `BOT_DEATH`.
- `STUCK` and `ACTION_LOOP` are counter-only (`tortoisebots_anomalies_total`): `STUCK` never enters the Incidents ring buffer (the 60 s `STUCK` issue episode is the surfaced signal) and `ACTION_LOOP` never opens an issue episode (cooldown-gated to one event/30 s, so it almost never reaches a surface gate).
- `BOT_DEATH` is emitted from `PlayerbotAI::OnDeath` (target/zone/position/level/strategy) and is the one anomaly exempt from the `(guid, type)` 30 s cooldown: it is an event, not a sustained condition, so two deaths in one window are two rows. Every other emitter keeps the cooldown.
- Dead bots report `hp: 0` in the roster snapshot (the core's `GetHealth()` returns 1 for a corpse, which made corpse bars read "1 HP").
- `UNREACHABLE_TARGET` judges the AI's `current target` value, only while the AI runs its combat engine, not the client selection (which outlives the fight): it fires when that hostile unit stays more than 45 yd away or out of line of sight for 10 s, and the clock restarts when the AI changes target. Its `target` is that unit, so it can differ from the snapshot `target` (the selection); its `last_action` is the bot's real last combat-engine action, not a fixed label, and `type` alone marks the event as unreachable.
- Anomaly emitters that can persist (`UNREACHABLE_TARGET`) re-report every cooldown window so the daemon has a liveness signal; do not make them fire-once.
- `SERVER_INFO` datagrams (startup + every 5 min) carry module/core versions, live core rates and `AiPlayerbot` flags from running getters — never config files. The dashboard Server panel renders them, and its **Copy diagnostic report** button turns them plus pool health (tracked/gaining, median/total XP/h, deaths/min, combat/grind %, level bands), issue counts and freshness into a paste-ready plain-text snapshot (no secrets) — the way to report issues.
- **Core revision**: the module probes the core checkout itself (`TortoiseBots.cmake`, `git -c safe.directory=…`) and passes it as `TORTOISEBOTS_CORE_REVISION`/`_DATE`; `ModuleVersion.h` falls back to the core's own `REVISION_HASH`/`REVISION_DATE`. The core's CMake detection uses a plain `git rev-parse`, which git refuses in the containerised dev builder (root-owned bind mount) so it silently bakes in "unknown"/epoch — hence the dashboard showing `core unknown 1970-01-01` for a core that was built that way.
- **Bot tuning settings** in `SERVER_INFO.bots` (all read from the running config, not files): `bot_loot_uncommon`, `bot_loot_rare`, `ah_market`, `auto_learn_trainer_spells`, `auto_learn_quest_spells`, `level_up_mounts`, `turtle_mount_at_level` — plus the pool/behaviour flags. The Server panel groups them as RATES / BOTS·POOL / BOTS·TUNING / BOTS·GROUPS / BOTS·WORLD / DIAGNOSTICS in one key/value row per setting, and the diagnostic report repeats them as a `- tuning:` line. Hovering a row (dotted label) explains in plain words what the setting does, followed by its config key; the texts live in `SETTING_HELP` in `web/static/js/app.js` and summarise `aiplayerbot.conf.dist`, so update them when a setting's meaning changes.
- `/api/v1/grinding` serves the pool rollup behind the Grinding panel: per-bot XP/h + last-gain age over a 30 min level-up-aware window, pool gaining %, median/total XP/h, deaths/min + died-in-5-min % (from `BOT_DEATH` anomalies), combat/grind %, and level bands. Bands are per level while the pool spans <= 10 levels, otherwise five-level buckets 1-5/6-10/.../56-60; each band carries `avg_item_level` + `gear_bots` (see the gear sweep below).
- **Remote commanders (`COMMANDERS`, protocol v9).** `ObservabilityEmitter::EmitCommanders` sends one `COMMANDERS` datagram per 2 s snapshot cycle while at least one `.bot commander` binding stands, and one empty list when the last ends; nothing is sent (and the provider returns at once) while none exists, so an idle server pays a lookup per cycle. Above 8 bindings or 64 bots one cycle arrives in parts: a part holds at most 8 bindings, 64 bots and 64 mobs (a binding is never split), every part keeps the same payload budget, and `part`/`parts` ride after `seq` only when there is more than one (a single-part cycle is byte-identical to before parts existed); up to 20 bindings (the module's cap) and so at most 20 parts. Each part also stays at or under 60 000 bytes once fully serialized (UDP's 65 507-byte limit with room to spare); a binding that alone still goes over drops its mob overlays, then its objects, then its run's step notes, then its ready facts, and carries `trimmed: true`, logged once a binding per minute. Per binding: `commander` (name, `online` = has a network session), `view` (the TBM:VIEW feed is on), `group`, `lead`, up to 6 `bots` (name, guid, class, role, level, hp/max_hp, power/max_power, `power_type`, `alive`, `lead`, map, zone, x/y/z — the same readers and rage normalisation as `BOT_BATCH`) and the commander's last 8 `orders` (`at`, `verb`, `detail` = its arguments as typed, `ok`, `result` = the ACK scope and count or the ERR `code: message`). Orders are noted where the reply is sent (`SendActionAck`/`SendActionError` in `BotCommands.cpp`, intent `cmd <verb>`, bound commanders only); the log is bounded (8 per commander, 16 commanders, text clipped) and cleared with the bindings. **Map data (additive; an older daemon ignores it, an older module omits it):** per binding `commander_pos` (`map`, `x`, `y`; only while the commander is online and in the world), `mobs_map` and `mobs` (the hostile-ish units near the lead: `id`, `entry`, `name` clipped to 24 bytes, `hp` percent, `x`, `y`, `victim` = whom it targets, `reaction` h/n/f, `kind` k critter / v civilian / g guard / u unattackable; absent `kind` = ordinary), and per bot `id` and `target`. Guids are decimal strings (a creature guid is 64 bits, more than a browser's JSON number holds); a mob's `victim` and a bot's `target` name another unit's `id`. The mob list is the one the commander's `TBM:VIEW` feed builds (`CollectViewSnapshot`: the bots' own cached lists resolved by guid on the lead's map, no grid or world scan), rebuilt once per 2 s cycle and only while a binding stands; at most 24 mobs per binding and 64 per datagram. Size: about 5 bots + 10 mobs = 5 KB per binding, a full binding (6 bots, 8 orders, 24 mobs) 8 KB, the worst case of one part (8 bindings, 64 mobs) 42 KB, under the 64 KiB UDP limit. `mobs` is sent even when empty, so the dashboard can tell "none near" from "not reported". The module code is `runtime/CommanderTelemetry.h` (standard library only, unit-tested by `tools/test_commander_telemetry.cpp`); `host/BotHostAdapter.cpp` registers the provider, `commands/BotCommands.cpp` fills it. The payload describes what the module knows for any client of the commander protocol, not one client. The daemon keeps only the latest list (`internal/state/commanders.go`), calls it stale after 12 s without a datagram (a stopped server must not keep showing bindings), ignores datagrams of an older session or older `ts`, ignores a whole datagram of a cycle already applied (or an older one) as a duplicate while a datagram without a `seq` (an older module) is ordered by `ts` alone, and serves it as `GET /api/v1/commanders` and the `commanders` stream event. A cycle split into parts is collected per `(session, seq)` and applied once, when every part is in, with one stream event; a part of an older session, or of a cycle already applied, is dropped (it can neither join nor complete another session's cycle), and when the next cycle starts before a collection completed, the incomplete one is applied as a partial instead: its bindings stand and every commander it did not report is carried over from the previous list once (the second carry in a row drops it), counted in `tortoisebots_commanders_partial_total`. The stream then carries the applied list, so a partial's carried bindings reach it too. A binding that the module ends without a datagram (server down) simply goes stale.
- **The Commanders tab (one card per binding).** The tab draws only what `GET /api/v1/commanders` carries; the daemon API is unchanged. Wording, warnings and map math are pure functions in `web/static/js/commanders.js` (`CmdView`, no markup, loaded before `app.js`), unit-tested by `internal/commandersjs` (`go test ./...` runs `commanders_check.js` under node and skips where node is missing); `app.js` only draws. Each card has a one-line header (`Gbmage → 5 bots · Uldaman · fighting`: place from the lead's zone, state from the last accepted order and from what changes between reports), a warnings line, the party (role icon and colour: tank blue, healer green, DPS orange; class, level, HP and mana/rage/energy bars, yards from the lead), the last orders in plain words with the raw line on hover, and a small map. The module reports no combat flag, so the state word is an inference: an HP drop in the last 8 s is "fighting", an accepted attack/pull/focus/cc order in the last 15 s is "attacking"/"pulling", lead movement in the last 6 s is "moving", otherwise the last accepted order decides ("following", "holding position", "resting"), else "idle". Warnings: someone dead, a live bot under 30% HP, a bot over 40 yd from the lead or on another map, the newest order refused, the commander offline, the lead not reporting, and no report for over 30 s. The map is north-up at one unit a yard on a plain grid (spacing shown in its corner; the zone outline from the DBC bounds when the zone is known), bots as role-coloured dots with names, the lead ringed, and the lead's recent path (kept in the browser, up to 120 points). It fits the party and follows it by default; zooming (wheel, pinch, + / -) never turns following off (while following it zooms around the party in the middle, and keeps the zoom you chose as the party moves); only a drag pauses it, shown by a "Paused - click to follow" chip, and the chip or the Follow button resumes it. A binding's cards update in place on each stream event, so a drag or a tooltip survives the refresh. When reports stop, the last cards stay dimmed with a "No update for N s" warning (5 minutes, then dropped; an empty fresh list from the module clears them at once). Nothing here adds a dependency.
- **Raid bindings (Commanders tab).** A binding with more than 6 bots (or any bot with a `sub` subgroup) is a raid: the card shows the header plus `whyWaiting` (run state, note and seconds since it changed; `stalled` past 120 s, `stuck` past 300 s), the bots as subgroup blocks (`Group 1`–`Group 8`, 5 rows each, lead first; per row the same role/HP/power bars plus `act`+`res`, cast, target name, distance to the lead and an `away` badge), a Notes panel (the run's last 30 status lines, newest first), a Threat panel (mobs held on a non-tank for 2 s or more, red past 5 s), a Deaths panel (the last fights' deaths plus the bots now dead; a click centres the map on the spot), the map and order list, and a Controls row (Pause, Resume, Skip, Stop with confirm, Status, Start from leg and a "stop before the boss" checkbox that appends `until boss`, or alone sends `start until boss`, Revive dead one `.revive` per dead bot, Reload plans with confirm, Gear preset over `lkh zg aq20 timbermaw onyxia mc bwl es aq40 naxx kara40 prebis t1 t2`). Each button POSTs `/api/v1/control` with `X-TBM-Control: 1`; the answer shows under the row for 20 s; the row locks while one runs. The wording is pure functions in `commanders.js` (`raidBlocks`, `threatOffTanks`, `notesLog`, `deathsTimeline`, `controlLines`, `whyWaiting`), unit-tested in `commanders_check.js`; a 5-man binding renders as before. The demo (`#cmd-demo`, `demo.js` `raidFrame`) adds a simulated 20-bot raid card (`DEMORAID (simulated)`) with all panels filled.
- **Clicking a character (Commanders tab).** `COMMANDERS` carries `commander_guid` per binding (the commander character's low guid, also when offline; additive, an older module omits it and the daemon's `CommanderBinding.CommanderGUID` is then 0) next to each bot's `guid`. `CmdView.botHref(guid)` builds the dashboard's own route (`#/commanders?bot=<guid>`, the format `parseRoute` reads; non-numeric or out-of-range guids give no link), header/party/lead names are `a.cmd-botlink` links opened with `openProfile`, and a tap (movement under 6 px) on a map dot calls the same. Unit-tested in `commanders_check.js`.
- **Map layers and real maps (Commanders tab).** `web/static/js/maplayers.js` (`MapLayers`, no markup, loaded before `app.js`, unit-tested by `internal/commandersjs/maplayers_check.js`) holds the layer list, the defaults and the saved choice: 27 layers in 7 groups (Map, Party, Route, Threat, Raid, Events, Objects), with raid presets (Pathing, Trash pull, Healing, Boss, All; `PRESETS`/`applyPreset`/`presetOf`) that switch the raid's twelve keys at once, one `localStorage` key (`tbdash.mapLayers.v3`; a `v2`/`v1` choice is migrated once when v3 is missing, a merged layer on when ANY of its old switches was on, dim, path length and line styles carried over; a v3 saved with the old combined healer layer carries it into the healer-range and commander-line layers) for every card and map, holding the layer switches, `dim` (how much the real map picture is darkened, 0-80 %, default 30 = what it was before the slider), `trailLen` and `trailSec` (the newest seconds of a path to draw: 0 = no cut, else 10-300, default 0). Defaults: picture, grid and scale bar, zone names, bots and lead mark, all bot names, health bars and status icons, lead path, the plan route and its stands, the run line, enemies (hostile + neutral), enemy names and boss marker, boss and elite facing, boss and elite casts and spell areas, threat colours and lines, aggro and wake rings, the fight debugger's deaths, and run events when there is an event; off: other members' paths, the commander line, critters, stalls, the action lines, subgroup colours, healer → tank lines, the healer ring, and objects. Each layer lists the old switches it merges (`parts`) and each old switch names the data it needs (`OLD_LAYERS.needs`); `app.js` computes what each card has (`cmdMapFacts`), the panel greys a layer only when NONE of its parts has data and says why, and the drawing skips it. `effective(state)` turns the 27 choices into the old keys (`mobhostile`, `trail`, `threatcolors`, ...) that the draw code reads. A Commanders card whose party is a live dungeon run (same map, a shared bot) also draws that run's `DUNGEON_MOBS` list, merged by guid with the commander feed's (the feed wins on the fields it carries), so the card shows every enemy the run knows rather than the feed's 24; `N of M enemies shown` appears when the module capped the list. Without a matching run a card draws the commander feed only (capped at its 24) and shows no `N of M` note. The mob, threat-line, bot-target, aggro-ring and commander layers are drawn from the report's map data (above) and stay greyed only for a module that does not send it (or while the commander is offline, for its own mark); hostile mobs are red, neutral grey, critters small; the aggro ring is a rough 20 yd guide around hostile mobs nobody fights yet (the plan's own rings come from `planoverlay.js`: each plan mob's detection range against the party's lowest level, or the scripted wake radius the plan serves as `wake_yd`); the lead's heading is derived from its movement (no facing in the report). Adding a layer: one entry in `DEFS`, one `ctx` flag in `cmdMapFacts` if it needs new data, the drawing in `drawCmdMap`, a line in `maplayers_check.js`; it then appears in the panel and on every map. The real game maps come from `TBDASH_MAP_DIR` (`internal/mapdir`): a folder of `minimap-extract` output (`<id>.png` + `<id>.json`, extras `<id>.<minimap|worldmap|navmesh>[-<n>f]`), the owner's extracted assets, **never committed**. `GET /api/v1/maps/<id>` answers 200 with the three picture slots in Zul'Farrak's order — World map (one entry per `-<n>f` floor), Minimap, Navmesh — each with `kind`, `floor`, `label` and `available`, and a missing one with a one-line `reason` from an optional `<id>.status.json` in the folder (`{"minimap":{"reason":"..."}}`, at most 64 KiB, read but never served) or the built-in reason (indoor dungeon, no mmaps, no `WorldMapArea` row). An available slot also carries `name`, `source`, `url` and the rectangle it covers in the map plane (`x = -west`, `y = -north`, `w = west - east`, `h = north - south`; game x is north and game y is west); a map the folder has no pictures for still answers with three missing slots (the page greys the Map picture layer with the reason), and 404 comes only with no folder at all. `GET /api/v1/mapfiles/<name>` serves only `.png`/`.json` regular files of that folder whose name matches the extractor's patterns (no separators, no links, never the status file), both behind the GM login; `GET /api/v1/commanders` says `real_maps`. Unset: the tab keeps its grid. Deploy: copy the folder to the host (`rsync -a --include='*.png' --include='*.json' --exclude='*' ~/turtle-agent-minimaps/ host:dir/`), mount it read-only into the container and set `TBDASH_MAP_DIR`.
- **Fight debugger run timeline (Commanders tab).** Above the raid frames the debugger draws one strip for the run: grey walking gaps, a gold block per fight (`P1`..`Pn`, from the fight list's `start` and `dur`), a red block for a fight whose `boss_name` is set, and a red ✕ at every death of the loaded fight details. The Replay button and scrubber play the raid across the run from `GET /api/v1/commanders/track` (one request per run, clamped to the daemon's 30 min window; the answer's `tracked` is false for a commander outside the 20 the daemon keeps positions for, and the page then says the replay is kept for the first 20 commanders only, instead of claiming the fight kept none; the 20 tracks share a 48 MiB budget charged in the memory they retain (rows, strings, shapes and slice capacity, plus a fifth of headroom): the track charging the most gives its oldest frame up, never below 5 min (150 frames) per commander, and only when every track is that short is a whole commander forgotten, least recently seen first); while scrubbed or playing the map draws `fdRunActive` through the same `FightReplay.botsAt` / `fdReplayBind` path as a single fight, and selecting a fight block or starting a fight replay stops the run playback. `fdRunModel` (pure, tested by `internal/commandersjs/fdrun_ui_check.js`) owns the blocks and deaths; the rail card's `dmg` and the checks' emphatic values are presentation in `app.js`. The debugger hides the toolbar's duplicate Layers button (`.cmd-card.fd-on .cmd-maptools [data-act="layers"]`), so the map's `Layers ▾` panel is the one control.

- **Fight debugger checks: non-tank lane stretches and route strays (B4).** Two more `FightDebug.checks(fight, layout, warnings, extra)` rows read what the card already has, so they cost no request: `extra.lanes` is the one `AggroLanes.lanes` result the lane strip draws, `extra.strays`/`packI`/`prevPackI` come from the plan view (`PlanOverlay.view(...).strays`, `PlanOverlay.fightPack`), and the extra is kept on `fd.details[key]` so the rail grades every fight the same way. **`lane_nontank`**: a lane segment is *held* when its kind is healer or damage dealer, the victim bot is alive in that frame and stands within 30 yd of the enemy (2D); consecutive held segments, any victim, form one stint; the row takes the lane with the longest stint over every lane, not only the 12 the strip shows (`LANE` in `web/static/js/aggrolanes.js`) and fails at 12 s, warns at 8 s, passes otherwise (or "none"). The numbers come from tonight's three recorded Onyxia attempts (`~/TortoiseBots-audit/tests/onyxia-attempts`): 1-3 samples (2-6 s) on a healer or damage dealer are a taunt bounce the 2 s samples cannot resolve; the long stints with the victim within 30 yd were lost threat (on the kept samples: attempt 1 8 s, attempt 2 8 s and 12 s, attempt 3 14 s), while the 26 trash fights of the walk runs never left the tanks (top non-tank damage taken 4-9 %). **`plan_strays`**: the plan's move steps strictly between the previous pack's step and the fight's own pack (`prevPackI < step < packI`) that pass inside a later pack's ring — a scripted wake ring fails, an aggro ring warns, four details are listed then `+N more`; a fight without a plan (`plan: ""`, a pocket fight) has no row, and a plan on another map supplies nothing. Positions are 2 s samples: a bounce shorter than 4-6 s is not seen, so the two rows never claim what the sampling cannot show.

- **Live stream (`GET /api/v1/live`, additive to v12).** A second stream beside the WebSocket, per commander and in real time: Server-Sent Events for exactly the commanders the open tab draws (`?commander=NAME`, 1..20, deduplicated and sorted; none, more than 20, a control byte or a name past 64 bytes answers 400 `{"error":"bad commander list"}`). The first frame is `snapshot` (`{"commanders":[<the asked bindings>],"live":[FightSummary,...],"updated_at":<unix s>}`), then one frame per accepted datagram: `commander` (a `COMMANDERS` binding plus `ts_ms`; the page applies it only while the WebSocket is down, so no report renders twice), `pos` (a `COMMANDER_POS` frame, dropped client-side when the viewer's refresh rate is slower than 2 s or paused; a pos frame's own arrival interval is the gap the dots glide over, so they reach the reported place within one frame instead of lagging the 2 s report), `events` (a `COMBAT_EVENTS` datagram as received), `fight_live` (a live fight opened, ended or expired), `fight` (a finished fight's list row) and `resync` (`{"dropped":N}` before the next frame when the stream's queue lost frames). The page opens the stream with the Commanders tab and closes it when that tab is left, so an idle tab holds no stream. Caps: 32 streams (`503` with `Retry-After: 10` past it), 64 frames per stream, dropped-oldest (the newest position matters; a newer full report repairs the rest), heartbeat `: ping` every 15 s, and every write moves its own deadline because the server's 15 s `WriteTimeout` would otherwise cut a long-lived response. Same login (rank >= `MIN_GM_LEVEL`) and same-origin rule as the rest of the API, and the stream is bound to that login: it ends at the session token's expiry and revalidates the account's rank against the realm database every 60 s, so a revoked or downgraded account is cut off at the next check (its next reconnect then fails the login). The page reconnects with `retry: 3000`, falls back to 2 s polling for a minute after three errors in a minute or on a 401/404 (an older daemon), and keeps the WebSocket as the roster's path. The map interpolates the dots between reports (`web/static/js/glide.js`: the last four samples a unit in the game server's own `ts_ms`, a per-card clock offset smoothed to its minimum over ten reports, and a render time 1.25 x the median report gap in the past, clamped to 300..2600 ms, so a dot always has a later sample to walk towards; past the newest sample it walks on for at most 300 ms then holds; it snaps on a map change, a death or a jump past 12 yd + 20 yd/s; a frame more than 2 s behind the newest server time, or from another datagram session, starts that card's samples, offset window and gap history over and is drawn as a snap (a smaller reorder is dropped), a frame never moves the clock back, while position frames run only they feed the delay, and a unit no report carried for 15 s is dropped; while anything moves a visible card's map it redraws: the map the viewer looks at (the open Fight debugger tab, or the only card) at up to 60 fps, every other visible map at up to 15 fps, at most 8 glide-only redraws per animation frame round robin, and a map off screen not at all (an IntersectionObserver marks each card's map, and one back in view draws once at once), a card's "Live events" strip lists its newest 12 fight events under the fights panel, and a live fight appears in the list with `"live": true` and no detail to load until its `COMBAT_FIGHT` arrives. Dots may lead their trail by up to 2 s: the trails are fed by the full reports only. Prometheus: `tortoisebots_live_clients`, `tortoisebots_live_dropped_total`, `tortoisebots_realtime_datagrams_total{type}` and `tortoisebots_realtime_bytes_total{type}`.

- **`COMBAT_EVENTS` (additive to v12, `"fmt":1`).** The module's fight as it happens, at most one datagram per group per `AiPlayerbot.ObservabilityRealtime.EventGapMs` (100 to 2000 ms, default 250): the fight header (`id`, `start`, `start_ms`, `plan`, `leg`, `step`, `kind`, `boss`, `boss_name`, `fight_ms`), `dropped` (events lost to the book's queue) and up to 32 raw events (`start`, `engage`, `death`, `taunt`, `interrupt`, `cast`, `end`, `t` in ms since the fight start). The daemon keeps one live row per commander for the SSE stream and the fights list (`internal/combat/live.go`): at most 200 events, `COMBAT_FIGHT` closes it, a `kept:false` end removes it, and a row with no datagram for 15 min is filed as `unfinished` so the debugger still opens it. The finished fight always arrives as `COMBAT_FIGHT` (twice) and replaces the live row. Datagrams are applied in the session's `seq` order: a repeated (UDP duplication), reordered or older-session one changes neither the header nor the events and pushes no frame on the live stream (the browser appends every `events` frame it receives); a newer session starts over from its own first seq. A live row is a fight only while the module's commander snapshot shows a hostile unit engaged with the group (`internal/combat/engaged.go`: a hostile mob whose `victim` is a group member, or damage the group dealt in the live window's 10 s `dps`): the fights list and the SSE `live` rows pass a parked group's row over, because buffs, consumables and heals on a parked raid keep the module's book open for hours. At most 32 events per datagram and 16000 bytes (the event count is halved until it fits, the events that did not fit stay queued and go out in order in later datagrams, and a single oversized event goes out with its texts clipped), at most 64 queued per book (the oldest are dropped and counted in `dropped`). - **The Agent maps tab (issue #1102, read-only).** `--agent-maps-dir DIR` (env `TBDASH_AGENT_MAPS_DIR`) points the daemon at the folder `turtle-agent map` writes run maps into: one SVG per run (and one single-file HTML replay with `--html`). The folder is flat, so `internal/agentmaps` serves only regular `.svg`/`.html` files directly inside it, only through GET/HEAD, and only behind the usual GM login; symlinks are followed only when they resolve to a regular file directly inside the folder. Names are one path component with no control character, no leading dot and a lowercase extension; `..`, absolute paths, backslashes, NUL and encoded traversal (`%2e%2e`, `%2f`, `%5c`, `%00`) are rejected before any filesystem call. The folder is re-resolved (`filepath.EvalSymlinks`) before every list and open and must still equal the directory resolved at startup; a renamed-and-replaced folder path is refused (404 plus a log line). The last path component is checked with `Lstat` immediately before the open, opened with `O_NOFOLLOW|O_NONBLOCK` on unix (`open_unix.go`; the non-unix fallback relies on the same-file check), and the opened descriptor must be regular and `os.SameFile` with that `Lstat`, so a symlink or FIFO swapped in after the check cannot be followed or block the request. The response is an `io.NewSectionReader` at the checked size, so a file that grows after the check cannot stream past the cap. Known limits: a hard link inside the folder to an outside file is served (indistinguishable from the file; keep the folder and its ancestors writable only by the operator, `fs.protected_hardlinks=1`), and a hostile writer inside a writable folder is outside the guarantee. The list is capped at `MaxFiles = 200`, newest first by mtime (ties by name); a served file at `MaxFileSize = 32 MiB`, larger is 413. `GET /api/v1/agent-maps` is also the feature probe: unset answers 200 with `{"files":[],"enabled":false}` (no file is served), so a
  dashboard load makes no failing request, and the page keeps the tab hidden; an older daemon's 404 is read the same way. SVG is `image/svg+xml` with a `default-src 'none'` CSP and `sandbox` (no script); HTML is `text/html` with `default-src 'none'`, inline script/style only, `connect-src 'none'` and `sandbox allow-scripts` (never `allow-same-origin`), and the page frames either kind without `allow-same-origin`. The list is drawn by `web/static/js/agentmaps.js` (`AgentMapsView`, node-tested by `internal/commandersjs/agentmaps_check.js`), which escapes every file name and percent-encodes the file URL; `app.js` renders the escaped markup and text. - **Trail breaks (no straight lines through walls).** A path is never drawn from where a bot was to where it teleported. Between two consecutive reports of a bot (not between stored points, so a long stand-still cannot hide a jump) the trail breaks when the bot is on another map, or moved farther than `12 yd + 20 yd/s * gap` (gap = seconds between the reports, counted from 1 to 30). 20 yd/s is above the fastest 1.12 ground mount (about 14 yd/s with speed buffs); at the 2 s reports that is a break past 52 yd, and the 30 s cap keeps a missed-reports silence from excusing a summon. The point after a break carries its kind as a fourth element: `"t"` teleport/summon, `"r"` the same jump while the bot was dead before or after it (spirit release, resurrection at the spirit healer), `"m"` arrived on another map (the old map's trail is dropped), and `"d"` marks where the bot died (and `"g"` is a plain gap with no icon: reports were lost in a pause of more than 1000 held reports) (a bot turning from alive to dead; the line goes on). A point marked `t`, `r` or `m` starts a new piece: the same rule runs in the daemon (`internal/state/commanders.go`, `JumpLimitYd`, so the API returns no joined pieces) and in the browser (`CmdView.trailEvent`, used by the lead's tracker and `CmdPaths.noteTrails`; the daemon's history keeps its kinds through `cleanPoints`). The map draws each piece on its own (`CmdView.trailSegmentsBroken`, the fade runs over the whole path), a swirl where a path resumed after a teleport/release/map change and a skull where the bot died, each with a hover text. The heading is taken from the piece after the last break. The Bots tab's breadcrumb trail (`internal/state/store.go`, `trailJump`) uses the same limit and starts over after a jump. Tested in `commanders_check.js`, `paths_check.js`, `drawing_check.js`, `commanders_test.go` and `store_test.go`.

- **Fight history across nights (`internal/history`).** Every finished `COMBAT_FIGHT` is written to disk by the one writer goroutine (the UDP goroutine only enqueues, a full 64-slot queue drops and counts the fight): `<history dir>/<commander dir>/<YYYY-MM-DD>.jsonl`, one file per commander per UTC day of `fight.start`, `O_APPEND`, 0700 dirs, 0600 files, no fsync. A short or failed write is truncated back to the file's size before it, so the next line never lands behind a fragment; when even that truncate fails the day continues in `<YYYY-MM-DD>-1.jsonl` (then `-2` and so on, all scanned and rotated like the day's own file) and the broken one counts as `file_broken`. The commander directory is the name with every byte outside `[A-Za-z0-9_-]` replaced by `_` plus `-` and 8 FNV-1a 32 hex digits of the raw name, so two names that sanitize alike never share one. The folder is `--fight-history-dir` (env `TBDASH_FIGHT_HISTORY_DIR`), by default `<dir of --activity-state-file>/fight-history`, and an empty path turns the history off. SIGTERM or SIGINT (a container restart) stops the HTTP server, joins the UDP listener and then closes the writer, which writes what is still queued within a 10 s deadline: the writer's pack lookup runs on its own context, so one still reading the world database at the deadline is cancelled, and the fights left unwritten are logged and reported instead of holding the process open. Limits: 30 days of files (older days deleted at start-up and once an hour; a file exactly 30 days old stays), 256 MiB in all (over it the oldest day files go first, across commanders; one that cannot be deleted stays counted and is retried, and while nothing can be freed new fights are dropped, the log line once a minute), 16 MiB per day file (a full day skips further fights that day, logged once per file), 20000 index rows (a full index forgets its oldest row, so the newest fights stay listed), and a fight waits six seconds before it is written so the tracker holds its last frames. Each line is `{"v":1,"session","key","saved_at","pack_key","pack","engaged","nontank_ms","nontank_longest_ms","warnings","fight"}`: no frames (a night of 3 KB replays is too big per night, so a past night has no replay), the fight exactly as the module sent it, the pack it belongs to (`plan#step`, `plan@step`, `boss:<entry>` or `eng:<entries>`) and the non-tank seconds of `internal/lanes` (the page's `lane_nontank` rule ported: held segments within 30 yd joined into stints), `null` when the fight is outside the kept track. `GET /api/v1/combat/history/days?commander=`, `GET /api/v1/combat/history?commander=&day=YYYY-MM-DD` (a strict day, else 400 `{"error":"bad day"}`) and `GET /api/v1/combat/packs?pack=&commander=&all=0|1` (a pack key of 1..200 bytes without control bytes, else 400; at most 50 rows) read the index under a read lock; `GET /api/v1/combat/fight/<key>` falls back to the line on disk and judges it with the same rules (`"hist":true`, `pack_key`). A disabled history answers `{"days":[]}` and `[]`. Metrics: `tortoisebots_fight_history_written_total`, `_dropped_total{reason}` (queue, total_cap, file_cap, rows, closed, file_broken) and `_broken_total` (lines the start-up scan skipped).
- **Fight history on the page (`web/static/js/fighthistory.js`).** The Fight debugger's rail head carries a Night picker (`FightHistory.dayOptions`: fixed English labels over UTC, `Tonight` first, today listed too (the live list holds only the fights since a restart, the earlier ones of today are on disk), the day's fight count) that opens a stored night from `GET /api/v1/combat/history` instead of the live list (`fdLoad` keeps that night's list 10 s; the live card is Tonight's only). `GET /api/v1/combat/history/commanders` lists the commanders with saved fights (newest fight first, with their fight and night counts), so the Fight debugger with no raid bound lists them under the one-line "No raid bound right now." note and each opens a read-only history card (day selector and rail, no live party or map). A past fight opens through the same `GET /api/v1/combat/fight/<key>` and its replay row says "No replay for past nights (positions are kept 30 min)"; no lane row is synthesized from the stored seconds. Under the checks, **Same pack across runs** (`FightHistory.packTable`, one request per pack per minute, an All commanders box) lists the pack's fights across nights with night, time, length, deaths, non-tank seconds and outcome, says the best attempt in words (fewest deaths, then shortest, then newest, kill or end only) and makes every time a button that opens that fight on its own night (a fight of today opens Tonight, the current list).
- `GET /api/v1/history` seeds the dashboard's 10-minute timelines (population, tick/lag, issues-over-time) after a refresh: the store appends one sample per heartbeat (`at` unix-millis, bots/humans, lag p50/p95 with the live chart's `lag||diff_avg||diff` fallback, per-type issue counts from the same tracker snapshot the Issues tab sees), capped at 300 samples (~10 min, oldest dropped). In-memory only — a daemon restart clears it — and clipped to the current game-server session (`since`), so a restarted server starts its charts empty. The page fetches it once on load, then live heartbeats keep appending.

## Issue episodes (`internal/state` issue tracker)

Persistent problems are tracked as open/closed episodes per bot, surfaced in the dashboard Issues tab, map glow, roster badge, and `/api/v1/issues`.

- Snapshot-derived: `STUCK` (moving state but position frozen >= 60s), `DEAD_LONG` (dead >= 2 min).
- Anomaly-derived: `UNREACHABLE_TARGET` only (refreshed by the emitter, expires after a 2 min TTL, or closes early when a snapshot contradicts it).
- **Minimum age**: only episodes that persist past their gate are shown (`ISSUE_MIN_AGE_SEC`, default 300s); shorter ones are discarded entirely. `UNREACHABLE_TARGET` carries its own 2 min lower gate — it can only shorten the configured minimum age, never lengthen it — because the snapshot contradiction bounds its false-positive risk. This is the guard against transient false positives — keep new detectors behind it.
- **Post-restart blackout**: no `DEAD_LONG` episode opens in the first 5 min after a game-server session change; the timer slides through the blackout so per-bot rows start timing only after it.
- Severity escalates `watch` -> `persistent` (>= 10 min).
- Resolved history survives a game-server restart (`Reset()` clears open episodes only); it is in-memory and bounded, so a daemon restart clears it.
- Metrics: `tortoisebots_issues_active{type}`; anomalies counted by type (including `BOT_DEATH`, counter-only `STUCK`/`ACTION_LOOP`).
- Incidents (`/api/v1/anomalies`) is a rolling last-1000-event window (~30 min at busy rates), not history; severity filters match case-insensitively.
- Cumulative session totals (`GET /api/v1/anomalies/totals`, same auth): per-type counts since the game-server session started plus the per-`last_action` breakdown for `ACTION_LOOP` / `UNREACHABLE_TARGET`, with `since`/`since_str` marking the window. Whole-run counts (`ACTION_LOOP` rows for the KPI report) come from here. Totals reset with the session (or a roster wipe); the dashboard's Clear wipes the feed only, and the Issues tab shows them as one totals line.

Eleven tabs, each answering one question, with no panel in two places: **Overview** (is everything running: player lag, bots/players, snapshot age, issues, population and player-lag charts, the live-state census whose rows jump to the Bots list, and a short needs-attention list), **Bots** (the one list of bots), **Map** (zone census chips + world/zone map), **Dungeons** (what is inside every instance copy: see the Dungeons tab below), **Agent maps** (the run maps `turtle-agent map` wrote, listed read-only and shown inline; off unless a folder is configured), **Commanders** (who leads which bots: one card per remote-commander binding with a one-line state header, warnings, the party with role colours and HP/power bars and distance to the lead, the commander's last orders in plain words, and a small follow/zoom/pan map; an optional link to the agent's live map below), **Progress** (pool XP/death KPIs, level bands with gear item level, level-up timeline), **Activity** (counters grouped by theme plus one feed panel switching between quests, loot and the live console), **Auction House** (read-only market view), **Issues** (KPIs, issues over time/by zone, then one panel switching between active issues, recently resolved and the incident feed) and **Server** (effective settings, diagnostic report).

- **One bot list.** `Bots` joins the database list (`GET /api/v1/armory/bots`: every pool bot plus every player-account character, online or offline, refreshed on tab activation and once a minute) with the live roster by guid. Live telemetry wins for everything it carries (kind included: pool/hired/claimed/alt/companion/player); offline bots show database values (level, spec, gold, kind) and a dash for the rest. State, kind and class chips double as the census and filters; the Live / Progress / Activity switch only changes the columns (the old per-bot activity table is the Activity columns). Default order is online first, then name.
- **Spec labels.** The spec is derived from the learned talent ranks (`character_spell` against Talent.dbc), so a character with no talent points has none: `spec` is empty, the Class column shows the class alone and no spec chip is offered (never a placeholder name — a level-60 test character with no talents used to read "Unspecified"). A shaman the server put on the tank role (`role: "tank"`: a forced role, a hired tank or the gear+talent detection) is labelled `Enhancement (Tank)` in the list and in the profile, while the filters, the chips and the class colour keep treating it as plain Enhancement; the label needs the live roster, so an offline shaman shows the plain name. `GET /api/v1/armory/bots` is capped at 10000 rows per half: a cap under the pool size silently drops bots from the list (and their database values with them).
- **One bot profile.** A slide-over opened from any tab (list row, map marker, issue/feed bot name, the topbar find-a-bot box or `/`): Overview (live status, issues, recent quest/loot events), Gear & stats, Talents, Spells, Professions, Skills, Bags, Activity. On the map it is a narrow side panel and the backdrop is click-through so another marker can be picked.
- **Auction House.** `GET /api/v1/auctions` (filters `q`, `quality`, `min_level`, `max_level`, `seller`, `kind`, `house`, `sort`, `dir`, `page`) reads the whole AH in two short statements (`auction` + `item_template`, then the sellers) and filters, sorts and pages in the daemon; stack counts and icons are fetched for the returned page only. `auction`, `characters` and `item_display_info` are MyISAM and `item_display_info` has no index on `ID`: joining either to every auction held table locks for seconds and stalled the core's character writes, so keep it that way. Default order is most time left (the core stores no listing time and refills freed auction ids after a restart).
- **Routing.** The URL hash is the single source of truth: `#/<tab>` or `#/<tab>?bot=<guid>&p=<profile tab>`. Back, reload and pasted links land on the same view; without a hash the last tab (kept in `localStorage`) is restored.
- Only the visible tab renders on each snapshot (list/map do the heavy DOM work and are skipped while hidden). Counters keep their session window label ("since 10:24"). The Issues table defaults to the ≥5 min filter so the 5–10 min "watch" cohort the card counts is visible (rows without a duration are kept, not hidden), and its "Deaths" card counts the `BOT_DEATH` rows currently in the incident list. The Gear column shows the swept average item level (quality split in the tooltip), and the level bands show `ilvl` with its ratio per level. The profile shows live health/power/XP for online bots (the armory DB has no live values), a max-only power bar for offline ones, and an "Equipped Gear" summary (average item level + quality split) above the paperdoll.

Bot profile: Spells and Professions are separate tabs (profession spells moved out of the spellbook groups into Professions, paired with live profession skill levels). The Skills tab dedupes by skill id (server `GROUP BY`, client highest-wins) and no longer lists professions. Talents render the three class trees in DBC page order (1.12 frame left-to-right), each as a 7-tier × 4-column grid from Talent/TalentTab row/column.

## Diagnostic report (recommended for bug reports)

The dashboard Server panel has a **Copy diagnostic report** button producing a compact plain-text (markdown) snapshot: module/core versions, effective rates and bot flags, the bot-tuning line (XP rate, loot rates, autolearn trainer/quest, level-up mounts, AH market), pool health (tracked/gaining, median/total XP/hour, deaths/min, died-5min %, combat/grind %, level bands with their average item level), a pool gear line (swept bots, average item level, equipped-piece quality census), pool activity counters (quests/loot/money/kills/deaths/ghost time/services), issue counts, and server freshness. A flag the running server did not report reads `?`, never a false "off". It contains no secrets (no IPs, hosts, account names, passwords). Paste it into a GitHub issue or Discord when reporting bugs — it answers "how is this server configured" without config-file archaeology.

## Map artwork (generated locally)

The zone/continent images are the WoW client's WorldMap textures (Turtle's
custom zones included). They are **not** in this repository and **not** in the
dashboard binaries: generate them once from your own client.

```bash
python3 -m pip install mpyq Pillow
python3 tools/observability/scripts/gen_zone_maps.py --data "<WoW>/Data" --out tools/observability/maps
```

`--out` defaults to `tools/observability/maps/`, which is where
`run-dashboard.sh` / `run-dashboard.ps1` put the binary. The binary serves
`maps/` next to itself; point it elsewhere with `--maps-dir` / `MAPS_DIR`
(e.g. a mounted folder in a container). Without the art the map tab still works:
a note replaces the picture and the bot dots stay on the same 1002x668 canvas.
The page asks for a continent or zone picture only when the Map tab draws it (the
images start with no source), so opening any other tab makes no map request.

How it is built: the client draws a zone as 12 base tiles (a 4x3 grid of 256px
textures, `Interface\WorldMap\<Zone>\<Zone><n>.blp`) plus one
`WorldMapOverlay.dbc` texture per sub-area that paints in the revealed detail.
The script composites both at their DBC offsets (instances and continents have
base tiles only) and writes each file at the canvas size recorded in
`web/data/map_canvas.json`: the daemon's world->map percentages are relative to
that canvas, so the sizes must not change. It reads Turtle's newer patches
(their file list is encrypted) and matches patch file names regardless of case.
Pass `--overlay-dbc` with the server's extracted `WorldMapOverlay.dbc` if the
client copy is unreadable.

## Security

- **Session secret (`SESSION_SECRET`)**: the `tbm_session` cookie is signed with HMAC-SHA256. There is no shipped default key — unset, the daemon generates a random key at startup and logs a warning, so dashboard sessions end on a restart. Set `SESSION_SECRET` (any random string) to keep sessions across restarts.
- **Login**: `/api/v1/auth/login` applies a per-IP in-memory backoff — 5 failed logins in a row block that address for 5 minutes. Every failure (wrong password, rank too low, blocked address) answers with the same error text, so it does not leak which part failed.
- **Bind address**: the dashboard binds `127.0.0.1` by default and is reachable only on the machine it runs on. For LAN or container access set `--http-host` / `HTTP_HOST=0.0.0.0` (`run-dashboard.sh` / `run-dashboard.ps1` pass the env var through; the Docker image sets it). Anything beyond localhost should sit behind a firewall or reverse proxy you control.
- **WebSocket**: `/api/v1/stream` accepts browser upgrades only from the same origin (Origin header must match the request host); non-browser clients are unaffected.
- **Live stream**: `/api/v1/live` needs the same GM session as the rest of the API and applies the same origin rule as the WebSocket (a present Origin header must match the request host; non-browser clients send none and pass). It is capped at 32 streams, so it cannot be used to pin memory.
- **`/metrics` is unauthenticated** (plain Prometheus text output: pool counters, no accounts or secrets). Expose the port only where a scraper can reach it, or scrape through a proxy that adds auth.

## Controls

`POST /api/v1/control` forwards one allow-listed GM line to the game server
over SOAP (`{"cmd": "<line>"}`) and answers `{"ok":true,"answer":"…"}` or
`{"ok":false,"error":"…"}`. Allowed: `.bot run for <Name> pause|resume|skip|stop|status`,
`.bot run for <Name> start [<plan>] [from <leg|step N>] [speed=<1.0-3.0>]`,
`.bot run reloadplans`, `.bot gear <Name> tier <0-7> [ilvl=<1-200>] [noenchants]`,
`.bot gear raid <Name> tier <0-7> [ilvl=<1-200>] [noenchants]`,
`.bot gear <Name>|raid <Name> preset <name>`, `.revive <Name>`. Anything else
(including `.bot commander status`) is refused. The relay needs a separate
rank-4 SOAP account on test servers only: `--soap-url` / `TBDASH_SOAP_URL`,
`--soap-user` / `TBDASH_SOAP_USER` and `--soap-password-file` /
`TBDASH_SOAP_PASSWORD_FILE` (a file holding the password, mode `0600` or
stricter, read once at start). Off unless all three are set: the route answers
`404`, `GET /api/v1/control` answers `{"enabled":false}` behind the GM login
for the page to hide the buttons, and the log names the missing setting,
never the credential. Guarded by the dashboard's own origin (`Origin` must
equal `scheme://Host`, header `X-TBM-Control: 1` required), a dashboard
session of rank >= `--control-min-gm` / `TBDASH_CONTROL_MIN_GM` (default 3),
one call in flight (`429 "busy"` while one runs) and a 10 s SOAP timeout
(`504`). Every call (refused ones too, after the session check) appends one
JSON line to `--control-audit` / `TBDASH_CONTROL_AUDIT`
(`control-audit.log` next to the activity state file by default):
`{"t":<unix>,"user":"…","cmd":"…","ok":<bool>,"answer":"<first 200 bytes>"}` —
the password never appears in the log, the error texts or the answer. Tests
use a fake SOAP server (`internal/control/*_test.go`); never a real one.

## Validation

No host Go toolchain is assumed: `docker run --rm -v "$PWD/tools/observability:/src" -w /src golang:1.22-alpine sh -c 'go vet ./... && go test ./...'`. Live check: the server logs `Observability telemetry active`, and `/metrics` (default port 8095) shows `mangos_server_online 1` and a rising `tortoisebots_snapshots_total`.

Operators without Go use the prebuilt binaries instead of building: every
daily release (`vYYYY-MM-DD`) carries
`tortoise-observability-linux-amd64` and
`tortoise-observability-windows-amd64.exe`, built by
`.github/workflows/dashboard-binaries.yml` (`go vet` + `go test` +
`CGO_ENABLED=0` static builds; also triggered by emitter wire changes).
Per-merge tags are plain git tags, not Releases, so binaries attach only to
the daily release (the workflow waits for it). The
one-command setup (`run-dashboard.sh` / `run-dashboard.ps1`) downloads the
binary, wires DB env from `mangosd.conf`, enables telemetry in
`aiplayerbot.conf`, and starts the daemon — see the operator guide above.
