# Observability daemon — developer notes

`tools/observability` is a standalone Go daemon (Prometheus + web dashboard) fed by `runtime/ObservabilityEmitter.{h,cpp}` over non-blocking UDP. It is optional and config-gated; core stays ignorant of it.

Rules that keep its state honest:

- The daemon has exactly one authoritative store (`internal/state`). REST, WebSocket, and Prometheus all read it.
- The emitter sends self-contained snapshot cycles: one `HEARTBEAT` + `BOT_BATCH` chunks sharing a `seq`. Publish a roster only from a complete cycle; clients replace their roster wholesale instead of merging deltas.
- Player lag: the heartbeat carries `lag_p50`/`lag_p95` (Prometheus `mangos_player_lag_p50_ms`/`_p95_ms`): how long a player's action waits before the server handles it, from the world-tick lengths of the last 30 s. An action lands in a tick with probability proportional to its length and waits for the rest of it (`runtime/PlayerLagWindow.h`). Against a headless probe client at 2000 bots it read about 15 ms under the measured p50/p95 (the time into the next tick before the player's map is processed is not modelled). This is the server's share of what a player feels; their ping comes on top, and the in-game latency meter never includes it (the core answers `CMSG_PING` on the network thread). `diff_avg`/`diff_worst` are the plain mean and worst tick of the same window.
- Every datagram also carries a `session` epoch (server process start). The daemon resets sequence/roster state when it changes, so a server restart that resets `seq` cannot be locked out as "old cycles".
- Bound and prune every emitter table (bot tracking, action failures, anomaly cooldowns) on each snapshot. Macro-state ratios are windowed, never lifetime totals.
- Anomaly types are a closed set (`model.AcceptedAnomalyTypes`) so Prometheus label cardinality stays bounded.
- `SERVER_INFO`'s `bots` object mixes numbers (pool sizes, intervals, budgets) with `"0"`/`"1"` flag strings: `ServerInfoPayload.Bots` is `map[string]any`. Typing it as `map[string]string` made `encoding/json` reject the whole datagram (silently, via the listener's error return), which left the Server panel and diagnostic report permanently empty.
- Add a datagram type to the daemon's `processPacket` switch: an unknown type falls to the anomaly parser and is dropped, which is also what an older daemon does with `COMMANDERS`.
- Bump `kProtocolVersion` in `ObservabilityEmitter.cpp` and `model.ProtocolVersion` in `internal/model/types.go` together.

## Telemetry surface (protocol v9)

Each `BOT_BATCH` bot entry carries: `name, guid, player, group, class, role, level, xp, next_xp, hp/max_hp, power/max_power, power_type, map, zone, x/y/z/o, target, target_level, strategy, state, last_action, last_trigger, travel_purpose, travel_to, travel_status, travel_dist, ai_visits, ai_age_ms`.

Real players ride the same snapshot cycle as bots: the emitter collects online network sessions (`HasNetworkTransport`, the same predicate behind the heartbeat `humans` count) every 2 s snapshot and appends one row per player with `player: true` and `group` = core group id (0 = solo). Bot-only detail stays empty (no role/strategy/AI age/travel); state is the visible unit state (combat/moving/resting/dead/idle). The daemon stores them in the same roster (list/map/profile join by guid) but excludes them from pool KPIs (grinding rollup, level bands), issue episodes, the level timeline and the class/role census; trails are bot-only. The Bots tab has a Bots + players / Bots / Players filter, player rows carry a "player" badge, map markers are rings in the class colour, tooltips and the profile show group instead of the AI role, and the profile skips the database subtabs (players are not pool bots). Heartbeat `humans` counts the same player rows the batches deliver; `bots` counts bot rows only.

`zone` (snapshot and event rows) is the zone the core caches on the bot (`GetCachedZoneId()`), not a terrain lookup. The core sets it at login and teleport and refreshes it on its one-second zone update, so at a zone border it can trail the bot's position by up to one second. Where the terrain has no area row, the cache keeps the last real zone instead of reporting 0.

Macro states (`state`, heartbeat `states`, `tortoisebots_state_ratio`): `combat` (in combat), `moving` (a movement generator owns the bot), `busy` (standing still but doing real work: looting, casting, sitting to eat/drink, movement within the last 45 s, or a fight/XP gain within the last 60 s), `stalled` (standing still for 45+ s whose only activity was churn — an active travel target or a changing last-action name, no movement/loot/cast/sit and no fight or XP gain in the last 60 s — i.e. standing with a destination and getting nowhere), `resting` (rest flag), `idle` (no movement, action, cast, loot, or active target for 45+ s — really doing nothing), `dead`. `stalled` exists so a bot parked with a travel target is no longer reported as busy. Per-tick cost is member reads + one action-name compare; the 3-min window is unchanged.
- `power_type` is the current resource (`mana`, `rage`, `energy`, `focus`, `happiness`); druids reflect their active form. Label bars by it, never hardcode "mana".
- `last_trigger` is the trigger that led to `last_action` (both are stored per engine state and change together, only when an action succeeds); failed or skipped attempts leave the pair untouched.
- `last_action`/`last_trigger` feed repeated-action detection; they are sampled per 2s snapshot, not per execution.
- Anomalies carry `guid` so the daemon can key episodes; accepted types are `STUCK`, `ACTION_LOOP`, `UNREACHABLE_TARGET`, `BOT_DEATH`.
- `STUCK` and `ACTION_LOOP` are counter-only (`tortoisebots_anomalies_total`): `STUCK` never enters the Incidents ring buffer (the 60 s `STUCK` issue episode is the surfaced signal) and `ACTION_LOOP` never opens an issue episode (cooldown-gated to one event/30 s, so it almost never reaches a surface gate).
- `BOT_DEATH` is emitted from `PlayerbotAI::OnDeath` (target/zone/position/level/strategy) and is the one anomaly exempt from the `(guid, type)` 30 s cooldown: it is an event, not a sustained condition, so two deaths in one window are two rows. Every other emitter keeps the cooldown.
- Dead bots report `hp: 0` in the roster snapshot (the core's `GetHealth()` returns 1 for a corpse, which made corpse bars read "1 HP").
- `UNREACHABLE_TARGET` judges the AI's `current target` value, only while the AI runs its combat engine, not the client selection (which outlives the fight): it fires when that hostile unit stays more than 45 yd away or out of line of sight for 10 s, and the clock restarts when the AI changes target. Its `target` is that unit, so it can differ from the snapshot `target` (the selection); its `last_action` is the bot's real last combat-engine action, not a fixed label, and `type` alone marks the event as unreachable.
- Anomaly emitters that can persist (`UNREACHABLE_TARGET`) re-report every cooldown window so the daemon has a liveness signal; do not make them fire-once.
- `SERVER_INFO` datagrams (startup + every 5 min) carry module/core versions, live core rates and `AiPlayerbot` flags from running getters — never config files. The dashboard Server panel renders them, and its **Copy diagnostic report** button turns them plus pool health (tracked/gaining, median/total XP/h, deaths/min, combat/grind %, level bands), issue counts and freshness into a paste-ready plain-text snapshot (no secrets) — the way to report issues.
- **Core revision**: the module probes the core checkout itself (`TortoiseBots.cmake`, `git -c safe.directory=…`) and passes it as `TORTOISEBOTS_CORE_REVISION`/`_DATE`; `ModuleVersion.h` falls back to the core's own `REVISION_HASH`/`REVISION_DATE`. The core's CMake detection uses a plain `git rev-parse`, which git refuses in the containerised dev builder (root-owned bind mount) so it silently bakes in "unknown"/epoch — hence the dashboard showing `core unknown 1970-01-01` for a core that was built that way.
- **Bot tuning settings** in `SERVER_INFO.bots` (all read from the running config, not files): `bot_loot_uncommon`, `bot_loot_rare`, `ah_market`, `auto_learn_trainer_spells`, `auto_learn_quest_spells`, `level_up_mounts`, `turtle_mount_at_level` — plus the pool/behaviour flags. The Server panel groups them as RATES / BOTS·POOL / BOTS·TUNING / BOTS·GROUPS / BOTS·WORLD / DIAGNOSTICS in one key/value row per setting, and the diagnostic report repeats them as a `- tuning:` line. Hovering a row (dotted label) explains in plain words what the setting does, followed by its config key; the texts live in `SETTING_HELP` in `web/static/js/app.js` and summarise `aiplayerbot.conf.dist`, so update them when a setting's meaning changes.
- `/api/v1/grinding` serves the pool rollup behind the Grinding panel: per-bot XP/h + last-gain age over a 30 min level-up-aware window, pool gaining %, median/total XP/h, deaths/min + died-in-5-min % (from `BOT_DEATH` anomalies), combat/grind %, and level bands. Bands are per level while the pool spans <= 10 levels, otherwise five-level buckets 1-5/6-10/.../56-60; each band carries `avg_item_level` + `gear_bots` (see the gear sweep below).
- **Remote commanders (`COMMANDERS`, protocol v9).** `ObservabilityEmitter::EmitCommanders` sends one `COMMANDERS` datagram per 2 s snapshot cycle while at least one `.bot commander` binding stands, and one empty list when the last ends; nothing is sent (and the provider returns at once) while none exists, so an idle server pays a lookup per cycle. Per binding: `commander` (name, `online` = has a network session), `view` (the TBM:VIEW feed is on), `group`, `lead`, up to 6 `bots` (name, guid, class, role, level, hp/max_hp, power/max_power, `power_type`, `alive`, `lead`, map, zone, x/y/z — the same readers and rage normalisation as `BOT_BATCH`) and the commander's last 8 `orders` (`at`, `verb`, `detail` = its arguments as typed, `ok`, `result` = the ACK scope and count or the ERR `code: message`). Orders are noted where the reply is sent (`SendActionAck`/`SendActionError` in `BotCommands.cpp`, intent `cmd <verb>`, bound commanders only); the log is bounded (8 per commander, 16 commanders, text clipped) and cleared with the bindings. **Map data (additive; an older daemon ignores it, an older module omits it):** per binding `commander_pos` (`map`, `x`, `y`; only while the commander is online and in the world), `mobs_map` and `mobs` (the hostile-ish units near the lead: `id`, `entry`, `name` clipped to 24 bytes, `hp` percent, `x`, `y`, `victim` = whom it targets, `reaction` h/n/f, `kind` k critter / v civilian / g guard / u unattackable; absent `kind` = ordinary), and per bot `id` and `target`. Guids are decimal strings (a creature guid is 64 bits, more than a browser's JSON number holds); a mob's `victim` and a bot's `target` name another unit's `id`. The mob list is the one the commander's `TBM:VIEW` feed builds (`CollectViewSnapshot`: the bots' own cached lists resolved by guid on the lead's map, no grid or world scan), rebuilt once per 2 s cycle and only while a binding stands; at most 24 mobs per binding and 64 per datagram. Size: about 5 bots + 10 mobs = 5 KB per binding, a full binding (6 bots, 8 orders, 24 mobs) 8 KB, the worst case (8 bindings, 64 mobs) 42 KB, under the 64 KiB UDP limit. `mobs` is sent even when empty, so the dashboard can tell "none near" from "not reported". The module code is `runtime/CommanderTelemetry.h` (standard library only, unit-tested by `tools/test_commander_telemetry.cpp`); `host/BotHostAdapter.cpp` registers the provider, `commands/BotCommands.cpp` fills it. The payload describes what the module knows for any client of the commander protocol, not one client. The daemon keeps only the latest list (`internal/state/commanders.go`), calls it stale after 12 s without a datagram (a stopped server must not keep showing bindings), ignores datagrams of an older session or older `ts`, and serves it as `GET /api/v1/commanders` and the `commanders` stream event. A binding that the module ends without a datagram (server down) simply goes stale.
- **The Commanders tab (one card per binding).** The tab draws only what `GET /api/v1/commanders` carries; the daemon API is unchanged. Wording, warnings and map math are pure functions in `web/static/js/commanders.js` (`CmdView`, no markup, loaded before `app.js`), unit-tested by `internal/commandersjs` (`go test ./...` runs `commanders_check.js` under node and skips where node is missing); `app.js` only draws. Each card has a one-line header (`Gbmage → 5 bots · Uldaman · fighting`: place from the lead's zone, state from the last accepted order and from what changes between reports), a warnings line, the party (role icon and colour: tank blue, healer green, DPS orange; class, level, HP and mana/rage/energy bars, yards from the lead), the last orders in plain words with the raw line on hover, and a small map. The module reports no combat flag, so the state word is an inference: an HP drop in the last 8 s is "fighting", an accepted attack/pull/focus/cc order in the last 15 s is "attacking"/"pulling", lead movement in the last 6 s is "moving", otherwise the last accepted order decides ("following", "holding position", "resting"), else "idle". Warnings: someone dead, a live bot under 30% HP, a bot over 40 yd from the lead or on another map, the newest order refused, the commander offline, the lead not reporting, and no report for over 30 s. The map is north-up at one unit a yard on a plain grid (spacing shown in its corner; the zone outline from the DBC bounds when the zone is known), bots as role-coloured dots with names, the lead ringed, and the lead's recent path (kept in the browser, up to 120 points). It fits the party and follows it by default; zooming (wheel, pinch, + / -) never turns following off (while following it zooms around the party in the middle, and keeps the zoom you chose as the party moves); only a drag pauses it, shown by a "Paused - click to follow" chip, and the chip or the Follow button resumes it. A binding's cards update in place on each stream event, so a drag or a tooltip survives the refresh. When reports stop, the last cards stay dimmed with a "No update for N s" warning (5 minutes, then dropped; an empty fresh list from the module clears them at once). Nothing here adds a dependency.
- **Clicking a character (Commanders tab).** `COMMANDERS` carries `commander_guid` per binding (the commander character's low guid, also when offline; additive, an older module omits it and the daemon's `CommanderBinding.CommanderGUID` is then 0) next to each bot's `guid`. `CmdView.botHref(guid)` builds the dashboard's own route (`#/commanders?bot=<guid>`, the format `parseRoute` reads; non-numeric or out-of-range guids give no link), header/party/lead names are `a.cmd-botlink` links opened with `openProfile`, and a tap (movement under 6 px) on a map dot calls the same. Unit-tested in `commanders_check.js`.
- **Map layers and real maps (Commanders tab).** `web/static/js/maplayers.js` (`MapLayers`, no markup, loaded before `app.js`, unit-tested by `internal/commandersjs/maplayers_check.js`) holds the layer list, the defaults and the saved choice: one `localStorage` key (`tbdash.mapLayers.v2`, read from `v1` once when `v2` is missing) for every card and map, holding the layer switches and `dim` (how much the real map picture is darkened, 0-80 %, default 30 = what it was before the slider), defaults = what the maps drew before layers (picture, grid, zone outline, bots, names, lead, path) and everything new off. Each layer names the data it needs (`needs`); `app.js` computes what each card has (`cmdMapFacts`), the panel greys a layer no card can draw and says why, and the drawing skips it. The mob, threat-line, bot-target, aggro-ring and commander layers are drawn from the report's map data (above) and stay greyed only for a module that does not send it (or while the commander is offline, for its own mark); hostile mobs are red, neutral grey, critters small; the aggro ring is a rough 20 yd guide around hostile mobs nobody fights yet; the lead's heading is derived from its movement (no facing in the report). Adding a layer: one entry in `DEFS`, one `ctx` flag in `cmdMapFacts`, the drawing in `drawCmdMap`, a test line in `maplayers_check.js`; it then appears in the panel and on every map. The real game maps come from `TBDASH_MAP_DIR` (`internal/mapdir`): a folder of `minimap-extract` output (`<id>.png` + `<id>.json`, extras `<id>.<minimap|worldmap|navmesh>[-<n>f]`), the owner's extracted assets, **never committed**. `GET /api/v1/maps/<id>` lists a map's pictures with the rectangle each covers in the map plane (`x = -west`, `y = -north`, `w = west - east`, `h = north - south`; game x is north and game y is west), `GET /api/v1/mapfiles/<name>` serves only `.png`/`.json` regular files of that folder whose name matches the extractor's patterns (no separators, no links), both behind the GM login; `GET /api/v1/commanders` says `real_maps`. Unset: the tab keeps its grid. Deploy: copy the folder to the host (`rsync -a --include='*.png' --include='*.json' --exclude='*' ~/turtle-agent-minimaps/ host:dir/`), mount it read-only into the container and set `TBDASH_MAP_DIR`.
- **Demo map (Commanders tab).** A switch above the layers panel (or `#/commanders?demo=1`; off by default) adds one extra card, "DEMO · simulated group", fed every 2 s by `web/static/js/demo.js` (`CmdDemo.frame`, pure, no server or module involved): a looping 140 s story on Uldaman (map 70; the picture comes from `TBDASH_MAP_DIR` as for a real map, else the grid) with a tank, healer, mage, hunter and warlock, hostile packs, a boss, a sheep and a fleeing mob, a neutral, a critter and a friendly unit, doors/chest/lever/gong, refused orders, a death, a boss kill and a wipe. The report goes through the same note and draw functions as a real one, is never put in `state.commanders.list` (counts, badge and the real cards do not see it) and its timer runs only while the switch is on. `internal/commandersjs/demo_check.js` fails when a layer in `maplayers.js` has nothing to show in the demo.
- **Unit info on the Commanders maps (additive `COMMANDERS` fields; hover box, bosses, health bars, icons, threat colours, events, run line).** The module adds, per bot (only while a binding stands, once per 2 s, from what the `TBM:VIEW` snapshot already holds plus field/aura reads): `st` (the AI state: c combat, n non-combat, d dead, r reaction), `act` (the engine's newest action name, clipped to 32 bytes) with `res` (its verdict letter), `cast` (the spell being cast or channelled, by name, 24 bytes), `cc` (s stunned, c confused i.e. polymorph/sleep, f fleeing, r rooted), `rest` (d drinking, e eating), `mv` (moving) and `tname` (the target's name, 24 bytes); per mob `lvl`, `rank` (b boss = world-boss rank or a creature that binds the instance, e elite, r rare), `cc` and `cast`; per binding `bound_at` (unix seconds the binding was first seen standing, kept in the emitter and forgotten when it ends). All are omitted when empty or unknown, so an older module's report keeps its shape and the page then says nothing about them (the *Status icons* layer is greyed with the reason). The pure logic is `web/static/js/unitinfo.js` (`UnitInfo`, loaded before `app.js`, tested by `internal/commandersjs/unitinfo_check.js`): `activity` (one phrase per bot: dead, crowd controlled, casting X on Y, drinking, fighting Y, moving, following ...; shown under each name in the party table and in the hover box), `describeBot` / `describeMob` / `describeCommander` / `describeEvent` (the hover box: name or entry, level, rank, reaction and kind, health, what it casts, whom it attacks, crowd control, yards from the lead), `boxPosition` (keeps the box inside the panel), `hpBar`, `threatClass` / `targetMarks` (a mob's ring is blue when it attacks a tank, red when it attacks another bot, none otherwise; the living tank's target gets a white outline and an unengaged mob some bot has picked a dashed gold ring: the pull target), `statusIcons` (skull dead, spark casting, sheep confused, stun, arrow fleeing, root, cup drinking/eating), and the events: deaths (a bot's `alive` turning false), a wipe (every bot down), a boss kill (a boss unit seen alive that leaves the list at 40 % health or less, or is listed at 0 %, while the party is not wiped; one that leaves sight healthier is not counted) and objects opened or looted (an accepted `open`/`use`/`loot` order that arrives after the page first saw the binding). Events live in the browser only (80 per binding) and start when the page does. The run line is `Run mm:ss` from `bound_at`, `bosses <killed> / <seen so far>` and the next boss seen alive; the module reports no dungeon plan, so there is no section count here (the agent's dashboard has the plan). The hover box appears when a mouse rests on a unit and, on a touch screen, on a tap (a second tap on a bot opens its details); it is built with `textContent` only. Layers (all in the one global Layers panel; defaults are what the maps drew before plus the boss marker and the health bars): `hostilenames` (off), `bossmark` (on), `threatcolors` (off), `hpbars` (on), `statusicons` (off), `events` (off), `feed` (off), `runinfo` (off); `botnames` is the switch for the group's names. Payload cost: the extras add about 60 bytes per bot and 25 per mob; the worst case (8 bindings of 6 bots and 64 mobs, all names at their clip) is 54 KB, tested to stay under 60 000 bytes (`tools/test_commander_telemetry.cpp`).
- **Drawing on the Commanders maps: paths, objects, stall spots, aggro rings, combat lines.** All layers sit in the one global Layers panel; every line layer (`trail`, `membertrails`, `threat`, `bottarget`, `healline`, `ccline`, `aggro`) has its own **Opacity** (10-100 %) and **Thickness** (50-300 %) sliders (shown while the layer is on), and one **Path length** slider (10-240 positions) serves both path layers; all of it is saved in the browser with the other layer choices (`maplayers.js`, same `localStorage` key, every read and write in try/catch; an older saved choice gets the normal look). Defaults: the lead's path on, the other members' paths off, the rest off. **Paths** (`web/static/js/paths.js`, `CmdPaths`, unit-tested by `internal/commandersjs/paths_check.js`): the page keeps a bounded ring (240 positions, one per 2 yd of movement) per bot from the 2 s reports, the lead's in `CmdView`'s tracker (it also feeds the heading and the times), the others' in `CmdPaths`; the lead's is brighter and thicker, a member's is coloured by role. Server side the daemon keeps a short bounded history too (`internal/state/commanders.go`: at most 240 points per bot, one per 2 yd, a new trail on a new map, forgotten with the binding or when the report goes stale; memory only) and serves it at `GET /api/v1/commanders/trails` (`{"<commander>": {"<bot guid>": {"map": 209, "pts": [[x, y, unix seconds], ...]}}}`); the page asks once per new binding and puts the older points in front, so a page opened mid-run starts with the paths already drawn. **Stall spots**: a red cross where an order was refused (a `move` at the point it named, other orders where the lead was at that second, from its path), noted by the page when it first sees the report and kept 15 minutes (12 at most); no new module field. **Objects**: per binding `objects[]` (`id` decimal string, `entry`, `name`, `x`, `y`, `type` d door / c chest / b lever / g gong or altar / r ritual / o other, `state` r closed / a open / u used), at most 16 (24 stored), from the bots' already calculated `nearest game objects` lists (never a grid scan), nearest to the lead first; `null` = not reported. **Aggro rings** use each mob's `lvl` against the lead's level: 20 yd at equal level, one yard more per level above, one less per level below, clamped to 5-45 (a vanilla rule of thumb, not the core's exact value); patrol paths are not drawn because the module does not send them. **Combat lines**: threat lines (mob to its `victim`, existing), bot target lines (existing), **heal lines** (a living bot casting at another party member, from the new per-bot `ctgt` = the spell's unit target, a decimal-string guid sent only while `cast` is; a healer with no `ctgt` falls back to its selection) and **crowd-control lines** (a caster whose `ctgt` is a mob that has `cc`). Payload cost: objects ~110, `ctgt` ~30 per casting bot; the worst case (8 bindings, every cap reached) is under 60 000 bytes, tested in `tools/test_commander_telemetry.cpp`. Old module: no `objects` or `ctgt`, the layers stay greyed with their reasons and everything else is unchanged.
- **Link to the agent's live map (`TBDASH_COMMANDER_URL`).** A collapsed "Open the agent's live map" section under the cards links to an external commander dashboard (for example `turtle-agent dashboard`, `http://127.0.0.1:8790`) and shows it in a frame only when the viewer opens it (nothing is requested before that). It is opt-in: set the env var (or `--commander-url`) to an `http://` or `https://` URL with a host and no credentials; anything else is logged and ignored. `GET /api/v1/commanders` carries it as `external_url`; unset, the field is absent and the section does not appear. The daemon never contacts that URL itself, only the viewer's browser does, so `127.0.0.1` means the viewer's own machine. The frame needs the other dashboard to allow framing from this page's address (turtle-agent allows loopback pages; `--embed-from` adds more), and an `https` dashboard cannot frame an `http` URL (mixed content): the section keeps an "Open it in its own tab" link for that.
- `GET /api/v1/issues` serves the same `store.Issues()` episode snapshot the WebSocket pushes, so the Issues tab, sidebar badge and map glow recover after a missed event or a Refresh.
- Gear sweep (item level): `armory.GearRollup()` runs **one** character-DB query every 5 min (`cmd/server/main.go`, never per tick) — equipped slots 0-18 minus shirt (3) and tabard (18), joined to `world.item_template` — and folds it per bot into average item level + quality census (`grey/white/green/blue/epic`, epic-or-higher bucketed into `epic`). `Store.SetGear` replaces the map wholesale (it is DB truth, not session state); each roster snapshot then carries `gear` per bot, level bands average it, and the armory profile computes the same summary from the profile's own equipment rows (identical slot rule). The dashboard shows it as the roster **Gear** column, the armory "Equipped Gear" summary, and the pool panel's `ilvl x.x · y.y×` per level band; the diagnostic report has a `- gear:` line.
- `BOT_EVENTS` datagrams carry the activity stream: the module mirrors a whitelist of `bot_events.csv` rows (`PlayerbotAIConfig::logEvent` → `ObservabilityEmitter::EmitBotActivity`) between the heartbeat and the roster batches of a cycle, so the roster published by the same cycle already carries the refreshed counters. Whitelisted: quest accept/complete/turn-in/drop/travel, `StoreLootAction`, `GatherLoot`, `LootMoney`, `SellAction`, `BuyAction`, `RepairAllAction`, `TrainerAction`, `NearbyService` (kind = trainer/vendor/turn-in), `AhAction`, `AhBidAction`, `BotDeath`, the revive/repop events (ghost time), `ReachGiveUp`, and an explicit `Kill` event from `XpGainAction` — the CSV row cannot carry the kill/non-kill XP flag. Item events are enriched server-side with `ItemPrototype` quality/sell/buy (no DB); every event carries the bot's copper, from which the daemon derives earned/spent. The queue is bounded (2048 rows, dropped on overflow) and chunked 40/datagram; `logEvent` forwards even when `bot_events.csv` is not in `AllowedLogFiles`.
- **Quest completion** rides on `QuestCompleted` (emitted by `BotPlayerAdapter` from the core's own quest-complete hook), not on `QuestUpdateCompleteAction`: the latter is packet-driven and never fires for a headless bot session, so `quests_completed`/`open_quests` were structurally zero on the live dashboard. The daemon counts both names as "complete, not yet handed in".
- `/api/v1/activity` (summary + per-bot counters + level timeline), `/api/v1/activity/loot` (`min_quality`/`class`/`min_level`/`max_level`/`bot`/`limit`), `/api/v1/activity/quests` (`bot`/`limit`) serve the Activity tab. Per-bot counters are also embedded in every roster snapshot as `activity`. All activity state is in-memory; per-bot counters are kept for every character that still exists; the 5-minute DB sweep forgets deleted characters (e.g. after a pool reset).
- **Counter window**: `summary.since`/`summary.since_str` report the start of the game-server session every counter covers, and the dashboard labels every counter panel with it ("since 10:24") — a bare `19 loot` must never read as a lifetime total. Feed rows (`/api/v1/activity/loot`, `/activity/quests`, the level timeline) carry `time_str`, the daemon's own rendering of the row timestamp, because formatting the epoch in the browser made the feeds disagree with the incident table (which has always used the daemon's time).
- **Persistence**: the rollup is snapshotted to one JSON file once a minute (`--activity-state-file`, default `<ICON_CACHE_DIR>/activity-state.json`, empty disables) and restored at startup, so a dashboard restart no longer resets the counters. Counters also carry on across a game-server restart; a new session (`beginSessionLocked`) only re-anchors money tracking.

- `GET /api/v1/history` seeds the dashboard's 10-minute timelines (population, tick/lag, issues-over-time) after a refresh: the store appends one sample per heartbeat (`at` unix-millis, bots/humans, lag p50/p95 with the live chart's `lag||diff_avg||diff` fallback, per-type issue counts from the same tracker snapshot the Issues tab sees), capped at 300 samples (~10 min, oldest dropped). In-memory only — a daemon restart clears it — and clipped to the current game-server session (`since`), so a restarted server starts its charts empty. The page fetches it once on load, then live heartbeats keep appending.

## Issue episodes (`internal/state` issue tracker)

Persistent problems are tracked as open/closed episodes per bot, surfaced in the dashboard Issues tab, map glow, roster badge, and `/api/v1/issues`.

- Snapshot-derived: `STUCK` (moving state but position frozen >= 60s), `DEAD_LONG` (dead >= 2 min).
- Anomaly-derived: `UNREACHABLE_TARGET` only (refreshed by the emitter, expires after a 2 min TTL, or closes early when a snapshot contradicts it).
- **Minimum age**: only episodes that persist past their gate are shown (`ISSUE_MIN_AGE_SEC`, default 300s); shorter ones are discarded entirely. `UNREACHABLE_TARGET` carries its own 2 min lower gate — it can only shorten the configured minimum age, never lengthen it — because the snapshot contradiction bounds its false-positive risk. This is the guard against transient false positives — keep new detectors behind it.
- **Post-restart blackout**: no `DEAD_LONG` episode opens in the first 5 min after a game-server session change; the timer slides through the blackout so per-bot rows start timing only after it.
- Severity escalates `watch` -> `persistent` (>= 10 min).
- Resolved history survives a game-server restart (`Reset()` clears open episodes only); it is in-memory and bounded, so a daemon restart clears it.
- Metrics: `tortoisebots_issues_active{type}`; anomalies counted by type (including `BOT_DEATH`, counter-only `STUCK`/`ACTION_LOOP`).
- Incidents (`/api/v1/anomalies`) is a rolling last-1000-event window (~30 min at busy rates), not history; severity filters match case-insensitively.
- Cumulative session totals (`GET /api/v1/anomalies/totals`, same auth): per-type counts since the game-server session started plus the per-`last_action` breakdown for `ACTION_LOOP` / `UNREACHABLE_TARGET`, with `since`/`since_str` marking the window. Whole-run counts (`ACTION_LOOP` rows for the KPI report) come from here. Totals reset with the session (or a roster wipe); the dashboard's Clear wipes the feed only, and the Issues tab shows them as one totals line.

Eight tabs, each answering one question, with no panel in two places: **Overview** (is everything running: player lag, bots/players, snapshot age, issues, population and player-lag charts, the live-state census whose rows jump to the Bots list, and a short needs-attention list), **Bots** (the one list of bots), **Map** (zone census chips + world/zone map), **Commanders** (who leads which bots: one card per remote-commander binding with a one-line state header, warnings, the party with role colours and HP/power bars and distance to the lead, the commander's last orders in plain words, and a small follow/zoom/pan map; an optional link to the agent's live map below), **Progress** (pool XP/death KPIs, level bands with gear item level, level-up timeline), **Activity** (counters grouped by theme plus one feed panel switching between quests, loot and the live console), **Auction House** (read-only market view), **Issues** (KPIs, issues over time/by zone, then one panel switching between active issues, recently resolved and the incident feed) and **Server** (effective settings, diagnostic report).

- **One bot list.** `Bots` joins the database list (`GET /api/v1/armory/bots`: every pool bot, online or offline, refreshed on tab activation and once a minute) with the live roster by guid. Live telemetry wins for everything it carries; offline bots show database values (level, spec, gold) and a dash for the rest. State and class chips double as the census and filters; the Live / Progress / Activity switch only changes the columns (the old per-bot activity table is the Activity columns). Default order is online first, then name.
- **One bot profile.** A slide-over opened from any tab (list row, map marker, issue/feed bot name, the topbar find-a-bot box or `/`): Overview (live status, issues, recent quest/loot events), Gear & stats, Talents, Spells, Professions, Skills, Bags, Activity. On the map it is a narrow side panel and the backdrop is click-through so another marker can be picked.
- **Auction House.** `GET /api/v1/auctions` (filters `q`, `quality`, `min_level`, `max_level`, `seller`, `kind`, `house`, `sort`, `dir`, `page`) reads the whole AH in two short statements (`auction` + `item_template`, then the sellers) and filters, sorts and pages in the daemon; stack counts and icons are fetched for the returned page only. `auction`, `characters` and `item_display_info` are MyISAM and `item_display_info` has no index on `ID`: joining either to every auction held table locks for seconds and stalled the core's character writes, so keep it that way. Default order is most time left (the core stores no listing time and refills freed auction ids after a restart).
- **Routing.** The URL hash is the single source of truth: `#/<tab>` or `#/<tab>?bot=<guid>&p=<profile tab>`. Back, reload and pasted links land on the same view; without a hash the last tab (kept in `localStorage`) is restored.
- Only the visible tab renders on each snapshot (list/map do the heavy DOM work and are skipped while hidden). Counters keep their session window label ("since 10:24"). The Issues table defaults to the ≥5 min filter so the 5–10 min "watch" cohort the card counts is visible (rows without a duration are kept, not hidden), and its "Deaths" card counts the `BOT_DEATH` rows currently in the incident list. The Gear column shows the swept average item level (quality split in the tooltip), and the level bands show `ilvl` with its ratio per level. The profile shows live health/power/XP for online bots (the armory DB has no live values), a max-only power bar for offline ones, and an "Equipped Gear" summary (average item level + quality split) above the paperdoll.

Bot profile: Spells and Professions are separate tabs (profession spells moved out of the spellbook groups into Professions, paired with live profession skill levels). The Skills tab dedupes by skill id (server `GROUP BY`, client highest-wins) and no longer lists professions. Talents render the three class trees in DBC page order (1.12 frame left-to-right), each as a 7-tier × 4-column grid from Talent/TalentTab row/column.

## Diagnostic report (recommended for bug reports)

The dashboard Server panel has a **Copy diagnostic report** button producing a compact plain-text (markdown) snapshot: module/core versions, effective rates and bot flags, the bot-tuning line (XP rate, loot rates, autolearn trainer/quest, level-up mounts, AH market), pool health (tracked/gaining, median/total XP/hour, deaths/min, died-5min %, combat/grind %, level bands with their average item level), a pool gear line (swept bots, average item level, equipped-piece quality census), pool activity counters (quests/loot/money/kills/deaths/ghost time/services), issue counts, and server freshness. A flag the running server did not report reads `?`, never a false "off". It contains no secrets (no IPs, hosts, account names, passwords). Paste it into a GitHub issue or Discord when reporting bugs — it answers "how is this server configured" without config-file archaeology.

## Map artwork (generated locally)

The zone/continent images are the WoW client's WorldMap textures (Turtle's
custom zones included). They are **not** in this repository and **not** in the
dashboard binaries: generate them once from your own client.

```bash
python3 -m pip install mpyq Pillow
python3 tools/observability/scripts/gen_zone_maps.py --data "<WoW>/Data" --out tools/observability/maps
```

`--out` defaults to `tools/observability/maps/`, which is where
`run-dashboard.sh` / `run-dashboard.ps1` put the binary. The binary serves
`maps/` next to itself; point it elsewhere with `--maps-dir` / `MAPS_DIR`
(e.g. a mounted folder in a container). Without the art the map tab still works:
a note replaces the picture and the bot dots stay on the same 1002x668 canvas.

How it is built: the client draws a zone as 12 base tiles (a 4x3 grid of 256px
textures, `Interface\WorldMap\<Zone>\<Zone><n>.blp`) plus one
`WorldMapOverlay.dbc` texture per sub-area that paints in the revealed detail.
The script composites both at their DBC offsets (instances and continents have
base tiles only) and writes each file at the canvas size recorded in
`web/data/map_canvas.json`: the daemon's world->map percentages are relative to
that canvas, so the sizes must not change. It reads Turtle's newer patches
(their file list is encrypted) and matches patch file names regardless of case.
Pass `--overlay-dbc` with the server's extracted `WorldMapOverlay.dbc` if the
client copy is unreadable.

## Validation

No host Go toolchain is assumed: `docker run --rm -v "$PWD/tools/observability:/src" -w /src golang:1.22-alpine sh -c 'go vet ./... && go test ./...'`. Live check: the server logs `Observability telemetry active`, and `/metrics` (default port 8095) shows `mangos_server_online 1` and a rising `tortoisebots_snapshots_total`.

Operators without Go use the prebuilt binaries instead of building: every
daily release (`vYYYY-MM-DD`) carries
`tortoise-observability-linux-amd64` and
`tortoise-observability-windows-amd64.exe`, built by
`.github/workflows/dashboard-binaries.yml` (`go vet` + `go test` +
`CGO_ENABLED=0` static builds; also triggered by emitter wire changes).
Per-merge tags are plain git tags, not Releases, so binaries attach only to
the daily release (the workflow waits for it). The
one-command setup (`run-dashboard.sh` / `run-dashboard.ps1`) downloads the
binary, wires DB env from `mangosd.conf`, enables telemetry in
`aiplayerbot.conf`, and starts the daemon — see the operator guide above.
